# Warehouse Solution — Development & Release Workflow

**Статус: INSTALLED via docs/workflow-v3 (pilot executed 2026-10-27), awaiting owner approval.** Этот файл предназначен для утверждения и установки в `warehouse_solution/docs/DEVELOPMENT_WORKFLOW.md` после локального безопасного пилота. До утверждения не меняет действующие правила `AGENTS.md` и production. Источник фактов: Git & Release Audit 2026-10-26.

## 1. Главный принцип

**Одна задача = один task-ID = один изолированный набор веток/worktree, одна область исследования всей системы, один согласованный набор PR, одна проверка совместимости.** Агент исследует все компоненты Warehouse Solution, но меняет только те, где нашёл причину. Длительная работа никогда не ведётся напрямую в общих `dev/main/prod`.

Важны три независимых понятия:
- **Source control:** Git SHA, ветки, PR, теги.
- **Execution environment:** DevStand, feature-env, staging, production.
- **Deployed release set:** набор версий сервисов, image digest, схем БД, frontend dist/hash, smoke/e2e результаты; хранится в release manifest в root-репозитории.

## 2. Роли веток после нормализации

| Реф | Роль | Кто изменяет |
|---|---|---|
| `feat/<task>-<slug>` | Изолированная функциональная разработка от согласованного `dev` SHA | Автор задачи через worktree |
| `fix/<task>-<slug>` | Исправление от **точного deployed SHA** компонента | Автор задачи через worktree |
| `dev` | Общая интеграция завершённых фич и backport хотфиксов | Только проверенные PR |
| `release/<id>` | Временная ветка выпуска **от текущего развёрнутого SHA** с выбранными изменениями | Release operator |
| `main` | Последний принятый релиз; не место для разработки | Release operator после выпуска |
| `prod` | Указатель на фактически развёрнутый Git SHA компонента | Release operator после успешного деплоя; только если возможен FF |
| `backup/*`, release tags | Архивные SHA и неизменяемые точки выпуска | По регламенту с записью в manifest |

**ПЕРЕХОДНЫЙ РЕЖИМ:** существующие `main`/`prod` расходятся и НЕ являются допустимой базой. Пока не проведена отдельно утверждённая нормализация, источник истины — **фактический образ и pinned SHA из release manifest**, а ветки `main`/`prod` остаются неизменными. Не делать `reset --hard`, force-push или merge ради «выравнивания».

## 3. Быстрый фикс без затягивания dev

1. Из фактического production release set получить SHA/Digest всех задействованных компонентов. Если нет уверенности в provenance образа, сначала подтвердить её, а не угадывать SHA из имени тега.
2. Создать `fix/<task>` **от deployed SHA** каждого изменяемого репозитория и отдельный worktree. Незадействованные компоненты фиксируются на deployed digest/версиях.
3. Внести минимальный фикс и регрессионный тест, протестировать в изолированной среде (для UI: Angular → Django → SyncServer → БД). Изменения не должны зависеть от незавершённого `dev`.
4. Открыть PR **в `release/<task>`**, созданную от текущего deployed SHA, пройти review и CI. Для нескольких репо — связанные PR с единым task-ID и manifest-кандидатом целого набора.
5. Собрать неизменяемые образы и проверить staging/smoke/e2e + миграции. Деплой делать **по digest**, не с помощью `git pull`/коммитов на VPS.
6. После подтверждения факта деплоя зафиксировать Git SHA, image digest, DB migration head, timestamps и проверки в `manifest/releases/prod.yaml`, а также release tag. Передвижение `prod`/`main` разрешено только когда отношения предок→потомок проверены; иначе ветки **оставить как есть**, решение о нормализации — отдельно.
7. Создать **отдельную backport-ветку от актуального `origin/dev`**; перенести только нужные исправления `git cherry-pick -x`, открыть PR в `dev`, пройти review и тесты. Не rebase и не merge `dev` в исходную release/fix-ветку, уже использованную для сборки.

Обязательное свойство: quick fix никогда не выпускается из общего `dev`; откат образа **не равен** откату данных/миграций. Для каждого изменения БД нужен совместимый rollback/forward-fix plan.

## 4. Большие фичи и параллельные агенты

1. `feat/<task>` создаётся от зафиксированного набора `dev` SHA по всем репозиториям. Даже если агент один, он работает в feature-ветке; основной DevStand не используется как writable workspace.
2. Агенту доступно полное дерево Warehouse Solution. Используется Multi-repo Solution Workspace: отдельные worktree изменяемых репо; неизменяемые зависимости pinned на SHA, весь набор записан в `feature.lock.yaml`.
3. Автономно проверять в `feature-env`; БД и контейнеры не пересекаются с соседними агентами. Для UI-работ нужны профили web/full, Angular HMR и кросс-сервисные e2e; это развитие текущего MVP.
4. На готовую задачу открываются связанные PR в затронутые репозитории, все отмечены task-ID. Пока PR ещё не готовы, можно использовать Draft PR. Порядок выпуска — по фактическим зависимостям, а не универсально `SyncServer → Django → Angular`: совместимость проверяется контрактами и матрицей наборов SHAs.
5. Выполнить review и CI каждого PR, затем совместный e2e на pinned release set. В `dev` сливать только законченные или выключенные feature-flag изменения. После каждого слияния обновить candidate lock и снова проверить совместимость.
6. Другие агенты подтягивают новый `dev` в собственные ветки **в своём worktree**; конфликт разрешается автором, без правок чужого checkout. `git stash` не является стратегией интеграции.
7. Релиз крупных фич собирается **от deployed SHA** с выборочным включением готовых коммитов/компонентных версий; не деплоить общий `dev` без проверки выбранного набора.

## 5. Ревью и CI

PR проверяет: минимальность изменения, тест на исходный дефект, корректный статус/транзакции/авторизацию, DB миграции и откат, совместимость старых клиентов, токены и секреты, изменения API, совместимость всего release set.

CI: статические проверки + быстрые тесты на каждый PR; полные тесты и e2e для release candidate. У текущей dev-ветки SyncServer в аудите есть 3 известные падения поиска; сначала задокументировать baseline и отделить новый регресс от старого, затем вводить обязательные зелёные проверки. Для sole-maintainer GitHub required approvals не включать без второго реального утверждающего аккаунта: автор PR не может заменить независимое GitHub-одобрение собственным review.

`git merge-tree` помогает предсказать конфликт, но не доказывает семантическую совместимость. `patch-id` — вспомогательный сигнал: при разрешении конфликтов он закономерно может измениться. Обязательны diff review, регрессионные тесты и проверка результата.

## 6. GitHub и деплой

- Прямой push в `main/prod` запрещён будущими rulesets/branch protection после пилота и настройки CI; для `dev` тоже PR-first после успешного теста процесса.
- На VPS не выполнять `git pull` для деплоя. Собрать на CI/devstand из pinned SHA, опубликовать образ в registry, развернуть по digest и smoke-проверить.
- `prod`-ветки сегодня расходятся с рантаймом. **Нельзя «исправить» это merge-коммитом**, потому что merge SHA не равен SHA реально исполняемого образа. До отдельной миграции canonical release fact = manifest + теги + image digest.
- `main` после миграции = последний подтверждённый релиз, не сборник будущих изменений; `release/*` = кандидат. При первой нормализации refs сохранить архивные refs и расписать изменение ссылок отдельно, с явным разрешением владельца.
- Для root-репозитория хранить `manifest/components.yaml`, `manifest/releases/candidate.yaml`, `manifest/releases/prod.yaml` и ссылки на task-ID и PR. Манифест **candidate** готовится до деплоя, **prod** фиксируется только по факту успешного деплоя.

## 8. Definition of Done для внедрения workflow

- Пилот фикс→PR→CI/review→стенд→release candidate→условный deploy→manifest→отдельный backport PR в dev (весь цикл без prod).
- Пилот параллельной фичи с настоящим конфликтом в Git worktree и проверкой итогового дерева.
- Подтверждённые фактические SHA и digest продовых образов, сохранённые в baseline release set.
- Документ установлен в root, `AGENTS.md` содержит ссылку, дублирующиеся правила помечены устаревшими; никакой реальный prod-ref не сдвинут до утверждения миграции.
