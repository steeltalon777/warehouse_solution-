### R-02 — `merge_items` переписывает `operation_lines.item_id`

- **Вердикт:** **confirmed**.
- **Evidence:**
  - `app/services/catalog_admin_service.py:833-839`:
    ```python
    reassign_result = await uow.session.execute(
        sa_update(OperationLine.__table__)
        .where(OperationLine.__table__.c.item_id == source_item_id)
        .values(item_id=target_item_id)
        .returning(OperationLine.__table__.c.id)
    )
    ```
    Физический UPDATE без сохранения исходного `item_id`. Модель `app/models/operation.py:307-311` — у `OperationLine` есть только `item_id`, поля `original_item_id` нет.
  - `:856` — в `changes` пишется только число `op_lines_reassigned_count`, не список строк.
  - Команда: `rg -n "original_item_id" app/` → 0 вхождений; `rg -n "reassigned" app/` → только count в `catalog_admin_service.py`.
  - Порядок исправлен по сравнению с аудитом (effects пишутся ДО мутации строк, `:754-828`), но сам риск переназначения строк не закрыт.
- **Предлагаемый фикс (Этап B-1/B-2 roadmap):**
  - Миграция: `OperationLine.original_item_id` (nullable) + backfill `= item_id`.
  - `merge_items` пишет в `original_item_id` source_item_id для переназначенных строк.
  - Отчётность/read-модель — через original_item_id.
  - Файлы: `app/models/operation.py`, новая миграция alembic, `app/services/catalog_admin_service.py`, `app/repos/` (read-запросы).
  - Оценка: **M–L** (миграция + backfill + правки отчётов). ADR: **нужен** (изменение доменной модели; кандидат ADR-0027 stage B).
  - Зависимости: R-20 (тот же merge-фикс).
- **Влияние на сезонную отчётность:** да. Уже совершённые merge необратимы: для строк, попавших в merge до фикса, исходный item_id утрачен навсегда (восстановимо только ручным walk через `audit_event_resources[merge_source]`). Рекомендуется перед закрытием сезона оценить масштаб: `SELECT COUNT(*) FROM items WHERE merged_into_id IS NOT NULL` + Q3 из SEASON_REPORT_READINESS §4. Если merges были — исторический отчёт по затронутым ТМЦ считать с ограничением.

### R-06 — late acceptance переоценивает баланс «на дату submit»

- **Вердикт:** **partial** — observability закрыта, политика cutoff отсутствует.
- **Evidence:**
  - Закрыто (Этап A-4, ADR-0028 §4.1/4.2): `app/services/operations_service.py:2539-2571` — per-action `operation.line_accepted` (с qty, progress before/after, action_id); `:2636-2668` — `operation.line_mark_lost`; `:2787-2810` — `operation.line_lost_resolved`; эффекты несут `cause_timestamp=action.performed_at` (дата фактического приёма).
  - НЕ закрыто: в `accept_operation_lines` (`:2452-…`) нет ограничения «accept только в пределах N дней от submit» — поздний приём по-прежнему разрешён; явной пометки «late accept» в событии нет.
  - Late accept детектируется проверкой `LATE_ACCEPTANCE` в `scripts/integrity_check.py:522-551` (порог по умолчанию 7 дней, severity=warning).
- **Тесты:** `tests/test_acceptance_audit_effects.py` (accept/mark_lost/mixed/resolve paths, отсутствие events при нулевом payload).
- **Предлагаемый фикс:** service-level guard в `accept_operation_lines` (например, `accept_operation_lines` отклоняет/помечает accept позже N дней от `submitted_at`; порог — конфиг/env). Файлы: `app/services/operations_service.py` (+ возможно `operations_workflow_policy.py`), тесты. Оценка: **S**. ADR: не обязателен, но нужно решение пользователя по порогу и поведению (блокировать vs помечать).
- **Влияние на сезонную отчётность:** числа корректны (effects датированы фактическим приёмом), но движение признанное в июле попадает в отчёт периода submit (`operation_at`). Для сезонного отчёта требуется явная политика: либо считать по `effective_at` (submit), либо исключать/помечать late accept.

### R-12 — restore + cancel + restore + new-submit создаёт «потерянный» cycle

- **Вердикт:** **partial** — журнал цикла восстановлен, guard отсутствует.
- **Evidence:**
  - Закрыта часть «нет audit»: см. R-03 — `operation.restore` с parent link на `operation.cancel`; повторный submit пишет свой `operation.submit` (`:2386-2400`).
  - НЕ закрыта часть «запрет restore, если с прошлой отмены операция была модифицирована (требуется review)»: такого guard в `restore_operation` (`:3148-3233`) нет — restore разрешён всегда, если статус cancelled; повторный submit после restore не блокируется.
  - Цикл теперь прослеживаем через audit-цепочку (cancel → restore → submit), но «потерянный» сценарий (многократный restore/re-submit с изменением состава) не запрещён.
- **Предлагаемый фикс:** guard в `restore_operation`: если операция после последней отмены была модифицирована (версия/состав строк), требовать review/подтверждение (или писать `changes["modified_since_cancel"]=True`). Файлы: `app/services/operations_service.py` + `operations_workflow_policy.py` + тесты. Оценка: **S**. ADR: не нужен.
- **Влияние на сезонную отчётность:** только будущее; для прошлых циклов журнал неполон (до фикса R-03), но данные балансов валидны.

### R-36 — отчёт чувствителен к back-date

- **Вердикт:** **partial**.
- **Evidence:**
  - `app/repos/reports_repo.py:32` — `operation_at = func.coalesce(Operation.effective_at, Operation.created_at)` — отчёт по дате операции, не по `audit_item_effects.effective_at`.
  - Будущее: backdating запрещён (R-01 refuted) → для новых операций effective_at консистентен.
  - Историческое: backdated операции (до ADR-0028) остаются; детектируются `BACKDATED_SUBMITTED` в `scripts/integrity_check.py:502-520` (severity=warning, по условию `effective_at < created_at AND status='submitted'`).
  - Бонус: A-6/ADR-0028 §7 — `exclude_system_effects=True` по умолчанию (`reports_repo.py:30, 56-57, 72-73, 88-89, 105-106`), фильтр `origin != 'system'` — системные merge/cancel ADJUSTMENT не смешиваются с ручными (закрывает также R-21/R-38).
- **Предлагаемый фикс:**
  - Обязательный разбор результата `BACKDATED_SUBMITTED` на проде перед закрытием сезона (ожидание 0; если >0 — решение: принять с обоснованием или пересчитать effective_at через миграцию/скрипт, требующую ADR).
  - Опционально: переключить `list_item_movement` на `audit_item_effects.effective_at` (единый источник даты журнала) — файлы `app/repos/reports_repo.py`, тесты отчётов. Оценка: **S–M**. ADR: только если меняется семантика отчёта.
  - Зависимости: R-01 (закрыт), R-05 (закрыт).
- **Влияние на сезонную отчётность:** да — исторический backdating может исказить распределение движения по периодам; до разбора Q1 (BACKDATED_SUBMITTED) сезонный отчёт по периодам считать с ограничением.

## Рекомендации

### Блокеры сезона (обязательны к фиксу/разбору до закрытия)

1. **R-02 + R-20 (merge)** — единственный P0 с необратимой потерей данных. Минимум: `original_item_id` (миграция + backfill `= item_id`) и per-line `relation='reassigned'` ресурсы для всех будущих merge; оценить масштаб прошлых merges (Q3). Требует ADR (доменная модель).

3. **R-06** — определить политику late acceptance (порог дней; блокировать или помечать) до закрытия сезона, т.к. это влияет на распределение движения по периодам.

### Перенос (Этап C roadmap)

6. **R-07** — таблица `source_documents` + storage + hash + parser version (M–L, нужен ADR). На числа сезона не влияет.
