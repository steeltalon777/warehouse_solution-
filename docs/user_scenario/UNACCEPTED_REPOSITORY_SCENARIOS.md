# Экран «Репозиторий непринятого»: пользовательские сценарии и acceptance-база

Документ описывает экран «Репозиторий непринятого» как основу для двух задач:

1. семантическая база для Playwright UI/acceptance-тестов;
2. будущий пользовательский раздел инструкции по работе с непринятым / ненайденным имуществом.

Репозиторий непринятого — это не «мусорка» и не место, где имущество загадочно испарилось. Это рабочий журнал расхождений при приёмке: что должно было приехать, но не было принято полностью или частично.

---

## 1. Назначение экрана

Экран «Репозиторий непринятого» показывает позиции ТМЦ, по которым при приёмке была зафиксирована недостача.

Пользователь должен быстро понять:

- какая ТМЦ не была принята;
- сколько не принято;
- по какой операции возникла недостача;
- на какой склад должно было поступить имущество;
- с какого склада оно пришло, если это перемещение;
- какой сейчас статус проблемы;
- когда запись была создана или обновлена;
- что можно сделать с этой недостачей.

Основные действия по непринятому:

- **Зачислить на склад** — если имущество позже нашли или оно всё-таки приехало;
- **Списать окончательно** — если имущество признано утерянным, повреждённым или окончательно не найденным.

---

## 2. Базовое доменное правило

Непринятое появляется только по результатам приёмки.

Типовой путь:

```text
операция прихода / перемещения
→ submit / подтверждение
→ приёмка
→ принято меньше, чем ожидалось
→ разница попадает в репозиторий непринятого
```

Запись в репозитории непринятого должна хранить связь с исходной операцией и конкретной строкой операции.

Непринятое не должно создаваться вручную без связи с операцией, если это не отдельный административный сценарий, явно описанный в домене.

---

## 3. Что такое «непринятый актив»

Непринятый актив — это конкретное количество конкретной ТМЦ, которое ожидалось при приёмке, но не было принято.

Пример:

```text
По операции прихода ожидали 10 баллонов кислорода.
Фактически приняли 5.
В репозиторий непринятого попадает 5 баллонов кислорода.
```

Для пользователя это означает:

- система помнит, что имущество должно было приехать;
- это имущество пока не числится в остатках склада назначения;
- по нему нужно принять решение;
- решение фиксируется отдельным действием.

---

## 4. Роли на экране

### Root

Может:

- видеть все непринятые позиции;
- фильтровать по всем складам;
- открывать любую запись;
- зачислять найденное имущество на склад;
- списывать имущество окончательно;
- видеть историю решений;
- исправлять ошибочные решения только через отдельное доменное правило.

### Главный кладовщик

Может:

- видеть все непринятые позиции;
- принимать решения по любому складу;
- зачислять найденное имущество;
- списывать окончательно;
- оставлять комментарии;
- контролировать расхождения.

### Кладовщик

Может:

- видеть непринятое согласно политике доступа;
- решать непринятое по своему складу назначения;
- зачислять найденное на свой склад;
- списывать окончательно, если это разрешено бизнес-правилами;
- оставлять комментарии.

Рекомендуемое правило:

```text
Кладовщик может решать непринятое только по своему складу назначения.
```

### Обозреватель

Может:

- видеть список непринятого;
- открывать карточку в режиме просмотра;
- смотреть связь с операцией и статус.

Не может:

- зачислять на склад;
- списывать окончательно;
- менять статус;
- оставлять решение.

---

## 5. Элементы экрана списка

На экране отображаются:

- заголовок «Непринятое / Ненайденное»;
- описание: «Позиции, по которым зафиксирована недостача при приёмке»;
- поле поиска;
- фильтр по складу;
- поле ID операции;
- кнопка «Применить»;
- кнопка «Сбросить»;
- таблица непринятых позиций;
- пагинация;
- выбор количества строк на странице.

В таблице отображаются колонки:

- ТМЦ;
- количество;
- операция;
- склад назначения;
- склад-источник;
- статус;
- дата;
- непринятое / действие.

---

## 6. Элементы карточки непринятого актива

Карточка открывается при нажатии на строку, ссылку операции или действие «Решить».

Карточка должна показывать:

- хлебные крошки;
- заголовок «Непринятый актив»;
- название ТМЦ;
- потерянное / непринятое количество;
- ссылку на исходную операцию;
- склад назначения;
- склад-источник, если применимо;
- статус;
- дату обновления;
- блок подтверждения решения;
- выбор действия;
- поле количества;
- поле примечания;
- кнопку «Подтвердить».

---

## 7. Статусы непринятого

Рекомендуемый набор статусов:

```text
open        открыто, решение не принято
resolved    решено
written_off списано окончательно
found       найдено и зачислено на склад
cancelled   отменено / закрыто администратором
```

Для UI можно отображать человекочитаемые статусы:

- «Открыт»;
- «Зачислен на склад»;
- «Списан окончательно»;
- «Закрыт».

Минимальное MVP-правило:

```text
Пока запись открыта, доступно действие "Решить".
После решения запись больше нельзя решать повторно.
```

**Дано:** пользователь вошёл в систему.

**Тогда:** открывается список непринятых позиций.

Пользователь видит:

- заголовок;
- описание;
- фильтры;
- таблицу;
- пагинацию;
- доступные действия.

Для Playwright:

```text
Проверить:
- заголовок "Непринятое / Ненайденное" виден;
- поле поиска видно;
- фильтр склада виден;
- поле ID операции видно;
- таблица видна;
- пагинация видна;
- нет бесконечного loader.
```

---

## UNACC-SCREEN-002: Список непринятого пуст

**Дано:** нет открытых непринятых позиций.

**Когда:** пользователь открывает экран.

**Тогда:** отображается понятное пустое состояние.

Рекомендуемый текст:

```text
Непринятых позиций нет.
Если при приёмке будет зафиксирована недостача, она появится здесь.
```

---

## UNACC-SCREEN-003: В списке отображаются открытые непринятые позиции

**Дано:** в системе есть непринятые позиции.

**Когда:** пользователь открывает экран.

**Тогда:** отображаются записи со статусом «Открыт».

В таблице должны быть видны:

- название ТМЦ;
- количество;
- операция;
- склад назначения;
- склад-источник;
- статус;
- дата;
- действие «Решить».

---

## UNACC-SCREEN-004: Пользователь открывает карточку непринятого актива

**Дано:** в таблице есть открытая запись.

**Когда:** пользователь нажимает «Решить» или открывает строку.

**Тогда:** открывается карточка непринятого актива.

В карточке пользователь видит:

- товар;
- непринятое количество;
- исходную операцию;
- склад назначения;
- статус;
- дату обновления;
- форму выбора решения.

# 9. Сценарии поиска и фильтрации

## UNACC-FILTER-001: Поиск по названию ТМЦ

**Дано:** есть непринятая позиция «кислород газообразный».

**Когда:** пользователь вводит `кислород` в поиск и нажимает «Применить».

**Тогда:** таблица показывает подходящие записи.

Поиск должен:

- работать по части названия;
- не учитывать регистр;
- игнорировать лишние пробелы.

---

## UNACC-FILTER-002: Поиск по номеру операции

**Дано:** непринятая позиция связана с конкретной операцией.

**Когда:** пользователь вводит номер или ID операции.

**Тогда:** таблица показывает непринятые позиции по этой операции.

Если поле называется «ID операции», оно должно принимать только корректный ID операции.

---

## UNACC-FILTER-003: Фильтр по складу назначения

**Дано:** есть непринятые позиции по нескольким складам.

**Когда:** пользователь выбирает склад назначения.

**Тогда:** таблица показывает только записи, связанные с выбранным складом назначения.

---

## UNACC-FILTER-004: Сброс фильтров

**Дано:** пользователь заполнил поиск, склад и ID операции.

**Когда:** нажимает «Сбросить».

**Тогда:**

- поле поиска очищается;
- склад возвращается к «Все склады»;
- ID операции очищается;
- таблица возвращается к исходному состоянию.

---

# 10. Сценарии появления непринятого

## UNACC-CREATE-001: Непринятое появляется после частичной приёмки прихода

**Дано:**

- операция прихода содержит 10 единиц ТМЦ;
- при приёмке принято 7;
- 3 отмечены как непринятые.

**Когда:** приёмка завершена.

**Тогда:**

- в репозитории непринятого появляется запись на 3 единицы;
- склад назначения указан корректно;
- склад-источник пустой или внешний;
- запись связана с исходной операцией;
- статус записи «Открыт».

---

## UNACC-CREATE-002: Непринятое появляется после частичной приёмки перемещения

**Дано:**

- перемещение со склада А на склад Б содержит 5 единиц;
- склад Б принял 3;
- 2 не приняты.

**Когда:** приёмка завершена.

**Тогда:**

- в репозитории непринятого появляется запись на 2 единицы;
- склад назначения = склад Б;
- склад-источник = склад А;
- операция указана;
- статус «Открыт».

---

## UNACC-CREATE-003: При полной приёмке непринятое не создаётся

**Дано:** операция принята полностью.

**Когда:** пользователь открывает репозиторий непринятого.

**Тогда:** по этой операции нет новых записей.

---

# 11. Сценарии решения: «Зачислить на склад»

## UNACC-RESOLVE-FOUND-001: Пользователь зачисляет всё непринятое количество на склад

**Дано:**

- есть открытая непринятая позиция;
- количество = 5;
- имущество позже найдено или приехало.

**Когда:**

- пользователь открывает карточку;
- выбирает действие «Зачислить на склад»;
- оставляет количество 5;
- нажимает «Подтвердить».

**Тогда:**

- 5 единиц зачисляются на склад назначения;
- запись получает статус «Зачислен на склад» или «Решено»;
- запись больше нельзя решить повторно;
- в истории фиксируется пользователь, время и комментарий;
- в остатках склада количество увеличивается на 5.

Для Playwright:

```text
Открыть запись со статусом "Открыт".
Выбрать "Зачислить на склад".
Ввести количество = максимуму.
Нажать "Подтвердить".
Проверить:
- статус изменился;
- остаток на складе увеличился;
- кнопка решения больше недоступна.
```

---

## UNACC-RESOLVE-FOUND-002: Пользователь зачисляет часть непринятого количества

**Дано:**

- непринято 5 единиц;
- найдено только 2.

**Когда:**

- пользователь выбирает «Зачислить на склад»;
- вводит количество 2;
- подтверждает.

**Тогда:** нужно выбрать доменное правило.

Вариант А:

```text
Исходная запись уменьшается с 5 до 3.
На склад зачисляется 2.
Запись остаётся открытой на оставшиеся 3.
```

Вариант Б:

```text
Создаётся новая история решения на 2.
Исходная запись закрывается частично.
Оставшиеся 3 создаются новой открытой записью.
```

Рекомендуемое правило для MVP:

```text
Разрешить только полное решение одной записи.
Частичное решение добавить позже.
```

Если частичное решение нужно сразу, его надо явно реализовать и отдельно покрыть тестами.

---

## UNACC-RESOLVE-FOUND-003: Зачисление найденного требует корректного количества

**Дано:** непринято 5 единиц.

**Когда:** пользователь вводит количество больше 5.

**Тогда:** система показывает ошибку:

```text
Количество не может быть больше непринятого.
```

---

# 12. Сценарии решения: «Списать окончательно»

## UNACC-RESOLVE-WRITEOFF-001: Пользователь списывает всё непринятое количество

**Дано:**

- есть открытая непринятая позиция;
- количество = 5;
- имущество признано утерянным.

**Когда:**

- пользователь выбирает «Списать окончательно»;
- указывает количество 5;
- вводит примечание;
- нажимает «Подтвердить».

**Тогда:**

- запись получает статус «Списан окончательно»;
- имущество не зачисляется на склад;
- в истории фиксируется решение;
- в общем журнале может появиться связанная операция списания или событие списания.

Рекомендуемое правило:

```text
Списание окончательно требует обязательного примечания.
```

---

## UNACC-RESOLVE-WRITEOFF-002: Списание без примечания запрещено

**Дано:** пользователь выбрал «Списать окончательно».

**Когда:** оставил примечание пустым и нажал «Подтвердить».

**Тогда:** система показывает ошибку:

```text
Укажите причину окончательного списания.
```

---

## UNACC-RESOLVE-WRITEOFF-003: Списание не изменяет остаток склада назначения

**Дано:** непринятое имущество ещё не было зачислено на склад.

**Когда:** пользователь списывает его окончательно.

**Тогда:** остаток склада назначения не увеличивается.

Если по доменной логике списание должно создавать отдельный документ, он должен быть связан с исходной операцией и непринятой записью.

---

# 13. Сценарии валидации формы решения

## UNACC-VALIDATION-001: Количество не может быть пустым

**Когда:** пользователь очищает поле количества и нажимает «Подтвердить».

**Тогда:** система показывает ошибку:

```text
Укажите количество.
```

---

## UNACC-VALIDATION-002: Количество должно быть больше нуля

Неверные значения:

- `0`;
- `-1`;
- отрицательные дробные значения.

Ожидаемо:

```text
Количество должно быть больше нуля.
```

---

## UNACC-VALIDATION-003: Количество не может быть больше максимума

**Дано:** максимум = 5.

**Когда:** пользователь вводит 6.

**Тогда:** подтверждение запрещено.

---

## UNACC-VALIDATION-004: Некорректный формат количества

Неверные значения:

- буквы;
- спецсимволы;
- несколько разделителей;
- пустая строка;
- слишком много знаков после запятой.

Ожидаемо:

```text
Некорректное количество.
```

---

## UNACC-VALIDATION-005: Действие не выбрано

**Когда:** пользователь не выбрал действие и нажал «Подтвердить».

**Тогда:** система требует выбрать действие.

Рекомендуемый текст:

```text
Выберите действие с непринятым количеством.
```

---

# 14. Сценарии прав доступа

## UNACC-PERM-001: Кладовщик решает непринятое по своему складу

**Дано:**

- кладовщик привязан к складу Угдан;
- непринятая позиция относится к складу Угдан.

**Когда:** кладовщик зачисляет найденное или списывает окончательно.

**Тогда:** действие успешно.

---

## UNACC-PERM-002: Кладовщик пытается решить непринятое чужого склада

**Дано:**

- кладовщик привязан к складу Угдан;
- непринятая позиция относится к складу Акша.

**Когда:** кладовщик нажимает «Подтвердить».

**Тогда:** сервер отклоняет действие.

Текст:

```text
Нет прав на решение непринятого по выбранному складу.
```

UI может скрывать кнопку, но сервер обязан проверить права.

---

## UNACC-PERM-003: Главный кладовщик решает непринятое любого склада

**Дано:** открытая запись по любому складу.

**Когда:** главный кладовщик принимает решение.

**Тогда:** действие успешно.

---

## UNACC-PERM-004: Root решает непринятое любого склада

**Дано:** открытая запись по любому складу.

**Когда:** root принимает решение.

**Тогда:** действие успешно.

---

## UNACC-PERM-005: Observer только смотрит

**Дано:** observer открыл карточку непринятого актива.

**Тогда:**

- форма решения недоступна;
- кнопка «Подтвердить» скрыта или disabled;
- прямой запрос на решение отклоняется сервером.

---

# 15. Сценарии статусов и повторных действий

## UNACC-STATUS-001: Открытая запись доступна для решения

**Дано:** запись имеет статус «Открыт».

**Когда:** пользователь с правами открывает карточку.

**Тогда:** доступен блок «Подтвердить решение».

---

## UNACC-STATUS-002: Решённая запись недоступна для повторного решения

**Дано:** запись уже зачислена на склад или списана окончательно.

**Когда:** пользователь открывает карточку.

**Тогда:**

- форма решения скрыта или заблокирована;
- отображается итоговое решение;
- повторное подтверждение невозможно.

---

## UNACC-STATUS-003: Решённая запись остаётся в истории

# 17. Негативные и конкурентные сценарии

## UNACC-EDGE-001: Двойное подтверждение решения

**Дано:** пользователь нажал «Подтвердить» два раза.

**Тогда:**

- решение применяется один раз;
- остатки меняются один раз;
- запись не создаёт дублей;
- кнопка блокируется после первого нажатия.

---

## UNACC-EDGE-002: Два пользователя решают одну запись

**Дано:** пользователь А и пользователь Б открыли одну запись.

**Когда:** пользователь А зачисляет её на склад, а пользователь Б позже пытается списать.

**Тогда:** пользователь Б получает сообщение:

```text
Запись уже решена. Обновите страницу.
```

---

## UNACC-EDGE-003: Пользователь потерял права во время работы

**Дано:** пользователь открыл карточку, когда права были.

**Когда:** root изменил его доступы, и пользователь нажал «Подтвердить».

**Тогда:** сервер отклоняет действие.

---

## UNACC-EDGE-004: SyncServer недоступен

**Дано:** пользователь открывает список или подтверждает решение.

**Когда:** SyncServer недоступен.

**Тогда:** UI показывает ошибку:

```text
Сервер склада временно недоступен. Попробуйте позже.
```

Данные не считаются сохранёнными, пока сервер не подтвердил действие.

---

## UNACC-EDGE-005: Запись удалена или закрыта во время просмотра

**Дано:** пользователь открыл карточку.

**Когда:** запись была закрыта другим пользователем.

**Тогда:** UI показывает понятное сообщение и предлагает обновить страницу.

---

## UNACC-EDGE-006: Ошибка при изменении остатков

**Дано:** пользователь выбрал «Зачислить на склад».

**Когда:** сервер не смог обновить остатки.

**Тогда:**

- запись не должна закрыться без зачисления;
- остатки не должны измениться частично;
- пользователь видит ошибку.

Рекомендуемое правило:

```text
Решение непринятого должно быть атомарным: либо статус и остатки обновлены вместе, либо ничего не изменено.
```

# 20. Что нужно уточнить перед финальной реализацией

Перед превращением документа в строгие автотесты нужно закрепить правила:

1. Разрешено ли частичное решение одной непринятой записи.
2. Если частичное решение разрешено, уменьшается ли исходная запись или создаётся новая запись на остаток.
3. Кто может списывать непринятое окончательно: кладовщик своего склада или только chief/root.
4. Должно ли списание непринятого создавать отдельную операцию списания.
5. Должно ли зачисление найденного создавать отдельную операцию прихода / корректировки или только событие решения.
6. Показывает ли список только открытые записи или все записи с фильтром статуса.
7. Нужно ли хранить историю решений в отдельной таблице.
8. Можно ли отменить ошибочное решение непринятого.
9. Нужно ли прикреплять фото / документы к решению.
10. Как отображать непринятое по временным ТМЦ, которые ещё не преобразованы в постоянные.

# 21. Краткая инструкция для пользователя

Экран «Репозиторий непринятого» показывает имущество, которое ожидалось при приёмке, но не было принято.

Чтобы решить непринятую позицию:

1. Откройте раздел «Репозиторий непринятого».
2. Найдите нужную позицию по названию ТМЦ, складу или операции.
3. Нажмите «Решить».
4. Проверьте товар, количество, операцию и склад назначения.
5. Выберите действие:
   - «Зачислить на склад», если имущество найдено или позже приехало;
   - «Списать окончательно», если имущество признано утерянным.
6. Укажите количество.
7. Добавьте примечание, особенно если выполняется окончательное списание.
8. Нажмите «Подтвердить».

После зачисления имущество попадёт в остатки склада.

После окончательного списания имущество не попадёт в остатки, а запись будет закрыта как решённая.

Если кнопка подтверждения недоступна, значит у пользователя нет прав на решение этой записи или запись уже закрыта.
