# Scope: доменные ошибки проведения операций (operation submit domain errors)

**Slug:** `SCOPE-operation-submit-domain-errors.md`
**Дата:** 2026-07-31
**Решение:** пользователь (кладовщик как источник боли, разработчик как постановщик)
**Источник проблемы:** кладовщик при подтверждении операции видит сырую серверную строку вида `insufficient stock for MOVE: inventory_subject=1655, source_site=1, required=2.000`, не понимает, каких ТМЦ и сколько не хватает, и не может быстро найти проблемные строки в накладной.

---

## 1. Проблема

Сейчас submit операций возвращает ошибки предметно, но **неструктурированно**:

* В `SyncServer/app/services/operations_service.py:1651-1790` все ошибки нехватки остатка (MOVE / ISSUE / ADJUSTMENT / WRITE_OFF / ISSUE_RETURN) поднимаются через `_ensure_sufficient_balance` с f-строкой в `detail`. В строке есть только `inventory_subject_id`, `site_id`, `required_qty`. Нет `operation_line_id`, нет имени ТМЦ, нет доступного остатка, нет единицы.
* `corrections_service.py:912` уже использует структурированный формат `{"code": "correction_insufficient_balance", ...}`, но без `items[]` / `errors[]`.
* `test_stale_balance_conflict.py:160, 207` валидирует ответ только по подстроке `"insufficient"` в `detail` — то есть контракт сейчас явно текстовый.
* `operations_workflow_policy.py:25` (неверное состояние), `operations_service.py` (stale version при `submit_operation`), `access_guard.py:81-115` (отсутствие прав operation permission) — каждый поднимает свою текстовую ошибку.
* На фронте `operations-screen-spec.md:651-659, 1184` уже описывает inline-подсветку «На складе: 3 шт / Количество: 5 / Ошибка: Недостаточно», но без серверной структуры эта подсветка опирается только на client-side валидацию и не закрывает server-side reject.
* Агрегированная проверка одинаковых ТМЦ в одной накладной (например, две строки одного кабеля по 60 м при остатке 80 м) на сервере сейчас не оговорена — каждая строка валидируется отдельно, что даёт ложное «всё ок» и роняет submit только по одной из них.

Цель: кладовщик при отказе submit сразу видит:

1. toast с кратким резюме («Не удалось провести: ошибки в N строках»);
2. inline-подсветку **именно тех строк**, на которых сервер отказал, включая агрегированные группы;
3. рядом с каждой проблемной строкой — `На складе: X ед., запрошено: Y ед.`;
4. фокус и скролл на первую проблемную строку;
5. понятные сообщения для всех остальных submit-ошибок (`stale_version`, `operation_in_wrong_state`, `temporary_item_blocked`, `role_not_permitted`).

---

## 2. Контекст и принятые ограничения

* Архитектурное правило: `SyncServer` — единственный источник истины, фронт получает данные только через Django BFF, в браузер не утекают SyncServer-токены.
* `app/services/operations_service.py` — sensitive area, изменения контракта требуют ADR.
* `Functional and WorkLogik.md` — канонический источник для типов операций, ролей и правил временных ТМЦ. Перед реализацией `temporary_item_blocked` нужно подтвердить наличие правила в спецификации.
* Оффлайн-клиенты (`Warehouse_client_core`, `WarehouseDesktop`, `WarehouseMobile`) в этой итерации **не учитываются** — формат проектируется под текущий Django + Angular стек.
* Django BFF пробрасывает ответ как есть: HTTP-статус, `detail`, `code`, `errors`, `trace_id`. Никакого склеивания обратно в строку.
* Количество (`required_qty`, `available_qty`) передаётся **строкой** — иначе `float` однажды вернёт `79.9999997` и откроет портал в бухгалтерскую преисподнюю.

---

## 3. Формат серверного ответа (контракт)

При любой доменной ошибке submit сервер возвращает Problem Details-подобный envelope. Структура:

```json
{
  "type": "operation_submit_rejected",
  "title": "Операция не может быть проведена",
  "status": 409,
  "code": "operation_submit_rejected",
  "detail": "Исправьте отмеченные ошибки и повторите проведение.",
  "instance": "/api/v1/operations/123/submit",
  "trace_id": "01JXYZ...",
  "errors": [
    {
      "code": "insufficient_stock",
      "scope": "line_group",
      "operation_line_ids": ["line-1", "line-4"],
      "item": { "id": "item-17", "name": "Кабель ВВГ 3×2.5" },
      "stock_site": { "id": "site-2", "name": "Склад Чита" },
      "required_qty": "120.000",
      "available_qty": "80.000",
      "unit": { "id": "unit-m", "name": "метр", "symbol": "м" }
    }
  ]
}
```

Ключевые решения по формату:

* `errors[]`, **не `items[]`** — не каждая ошибка относится к ТМЦ.
* Для одиночной ошибки по одной строке — `operation_line_ids: ["line-1"]` (массив из одного элемента). `operation_line_id` (скаляр) **не используется** — единый тип поля упрощает клиентский парсер.
* Для агрегированных ошибок (две+ строк одного `item` на одном `stock_site`) — массив `operation_line_ids` с длиной `>= 2`.
* Идентификация всегда по `id`, имена присутствуют только для отображения.
* Объект склада называется `stock_site`, не `site` — для MOVE критично явно отличать источник от назначения.
* Коды и ID — строки, чтобы не зависеть от типизации БД и не плодить маппинги на фронте.
* Старый клиент опирается только на `detail` (строка) и продолжает работать без изменений.

### 3.1. Структура одной записи `errors[]` по коду

| `code` | `scope` | Поля |
|---|---|---|
| `insufficient_stock` | `line_group` | `operation_line_ids[]`, `item`, `stock_site`, `required_qty`, `available_qty`, `unit` |
| `stale_version` | `operation` | `expected_version`, `actual_version` |
| `operation_in_wrong_state` | `operation` | `current_state`, `allowed_states[]` |
| `temporary_item_blocked` | `line` или `line_group` | `operation_line_ids[]`, `item`, `stock_site`, `reason` (по правилу из спецификации) |
| `role_not_permitted` | `operation` | `required_permission`, `actor_roles[]` (без привязки к строкам, в общем envelope) |

`errors: []` допустим — означает ошибку envelope-уровня (`role_not_permitted`, `operation_not_found`, `operation_in_wrong_state` без строк).

### 3.2. HTTP-статусы

| Код | HTTP |
| --- | ---: |
| `role_not_permitted` | 403 |
| `operation_not_found` | 404 |
| `stale_version` | 409 |
| `operation_in_wrong_state` | 409 |
| `insufficient_stock` | 409 |
| `temporary_item_blocked` (запрет по состоянию destination/site) | 409 |
| `temporary_item_blocked` (сама строка недопустима по правилу) | 422 |

Решение для `temporary_item_blocked` принимается в TZ после проверки правила в `Functional and WorkLogik.md`.

## 4. Архитектурные правила поведения сервера

### 4.1. Слои ответственности

```
Domain exception (InsufficientStockError, StaleVersionError, ...)
        ↓
API exception mapper (FastAPI exception handler)
        ↓
Problem response (JSON envelope)
```

Сервисный слой (`operations_service.py`, `corrections_service.py`, `operations_workflow_policy.py`) **не формирует JSON** и **не знает про HTTP**. Он поднимает доменные исключения с предметными данными (`StockDeficit`, `expected_version`, `actual_version`, и т.д.). Конвертация в envelope — задача отдельного exception handler, регистрируемого в приложении FastAPI.

`HTTPException(detail=dict)` запрещён — это сломает всех потребителей, которые ожидают строку в `detail`. Используется собственный класс `OperationSubmitError` с маппером.

### 4.2. Агрегация одинаковых ТМЦ

При проверке остатков сервер агрегирует строки операции по ключу `(stock_site_id, item_id, unit_id)` (или `(stock_site_id, item_id, base_unit_id)`, если конвертация единиц уже поддержана) и сравнивает сумму `qty` с доступным остатком. Если сумма превышает остаток — ошибка возвращает **все** строки группы в `operation_line_ids[]` с суммарным `required_qty` и общим `available_qty`. Это закрывает кейс «каждая строка отдельно валидна, вместе — нет».

Правила:

* Агрегируются только строки одного `stock_site` (для MOVE это `source_site_id`).
* Учитывается `unit_id` / `base_unit_id` — строки с разными единицами не склеиваются.
* Если хотя бы одна строка группы отдельно уже превышает остаток — это считается одиночной ошибкой, остальные строки группы не агрегируются (иначе дублирование).
* UI получает `operation_line_ids` и подсвечивает все указанные строки одним сообщением.

### 4.3. Порядок проверок (жёсткий)

1. Аутентификация и права (в т.ч. `role_not_permitted`).
2. Операция существует.
3. Состояние допустимо для submit (`operation_in_wrong_state`).
4. Версия актуальна (`stale_version`).
5. Бизнес-валидация строк (структура, обязательные поля, временные ТМЦ).
6. Проверка остатков (`insufficient_stock`, с агрегацией).
7. Проведение в одной транзакции.

Сервер **не возвращает одновременно** `stale_version` и `insufficient_stock`. Если версия устарела — клиент должен перечитать операцию и только потом разбирать остатки. Иначе пользователь будет править строки по протухшим данным.

### 4.4. Транзакционность

При любой ошибке submit:

* операция остаётся в прежнем состоянии;
* движения остатков не создаются;
* частичного проведения нет;
* повторный submit после ошибки безопасен (не создаёт дублей, не уходит в -∞ остаток).

Это **требует отдельного теста** на атомарность (`pytest-asyncio` + проверка `asset_register` до/после неудачного submit).

### 4.5. Django BFF

BFF пробрасывает как есть:

* HTTP-статус;
* `detail` (строка для legacy);
* `code`;
* `errors`;
* `trace_id`.

Никакого `json.dumps(errors)`, никакого склеивания `errors` в строку, никакой фильтрации. Иначе контракт для клиента деградирует до текста.

## 5. Поведение Angular

Это фиксируется как требования к TZ 2. Не решения, а контракт:

* toast показывает только краткое резюме: «Не удалось провести операцию: ошибки в N строках»;
* подробности показываются рядом со строкой (`:На складе: 80 ед., запрошено: 120 ед.`);
* при наличии ошибок экран прокручивается к первой проблемной строке и фокус переводится на её первое редактируемое поле;
* подсветка не должна зависеть только от цвета (иконка + текст + `aria-invalid="true"` — обязательно для a11y);
* после изменения строки её старая серверная ошибка очищается или помечается как «требует повторной проверки» (визуально отличается от свежей серверной);
* перед новым submit старые ошибки полностью сбрасываются;
* неизвестный `code` не ломает экран — показывается `detail`, неизвестная структура логируется в консоль;
* `errors: []` (envelope-уровневая ошибка) → только toast, без inline.

## 6. In Scope (что делаем в этой итерации)

### Сервер (TZ 1)

1. Ввести базовый класс `OperationSubmitError` (доменное исключение) и предметные подклассы: `InsufficientStockError`, `StaleVersionError`, `OperationInWrongStateError`, `TemporaryItemBlockedError`, `OperationNotFoundError`.
2. Зарегистрировать FastAPI exception handler, который превращает доменные исключения в envelope (см. раздел 3).
3. Переписать пять мест в `operations_service.py:1651-1790` (MOVE / ISSUE / ADJUSTMENT / WRITE_OFF / ISSUE_RETURN) на доменные исключения с агрегированным дефицитом.
4. Переписать stale-version проверку при `submit_operation` на `StaleVersionError`.
5. Переписать `operations_workflow_policy.py:25, 27` на `OperationInWrongStateError`.
6. Переписать `access_guard.py:81-115` (operation permission) на единый формат envelope без привязки к строкам.
7. Реализовать агрегацию строк по ключу `(stock_site_id, item_id, unit_id)` перед проверкой остатка.
8. Гарантировать транзакционность submit: единая транзакция, откат при любой ошибке, проверка тестом.
9. Зафиксировать порядок проверок (раздел 4.3) — ранее возвращаемые ошибки не должны маскироваться более ранними.
10. Обновить OpenAPI-схему: новые коды, структура envelope, примеры ответов.
11. Обновить существующие тесты, которые проверяют `detail` как строку (`test_stale_balance_conflict.py:160, 207`, и аналогичные) — теперь они проверяют `code`, `errors[]`, агрегацию.
12. Добавить новые тесты (раздел 8).

### ADR

13. Создать `docs/adr/0024-operation-submit-domain-errors.md` (или следующий свободный номер): контекст, выбранный формат, обоснование `errors[]` vs `items[]`, обоснование сохранения строкового `detail`, mapping кодов на HTTP-статусы, отклонённые альтернативы, стратегия миграции.

### UI (TZ 2)

14. Парсер envelope → нормализованная модель `OperationSubmitError`.
15. Toast-компонент с кратким резюме.
16. Inline-подсветка строк по `operation_line_ids` (включая агрегированные группы).
17. Скролл и фокус на первую проблемную строку.
18. Очистка ошибки строки при её изменении, сброс всех ошибок перед новым submit.
19. Fallback для envelope-уровневых ошибок (`errors: []`) и для неизвестных кодов — показ `detail`, логирование неизвестной структуры.
20. a11y: иконка + текст + `aria-invalid`, не только цвет.
21. Unit-тесты парсера, e2e Playwright-сценарии (раздел 8).

### Между TZ

22. Единый OpenAPI-фрагмент (или markdown-контракт) с JSON-схемой envelope и примерами по каждому коду. Этот контракт — single source of truth для обоих TZ. Никакого независимого описания JSON в двух TZ.

## 7. Out of Scope

* Offline-клиенты (`Warehouse_client_core`, `WarehouseDesktop`, `WarehouseMobile`) — формат envelope не оптимизируется под них.
* Нормализация **всех** ошибок API (auth, validation, 500, и т.д.) — только submit-flow.
* Client-side precheck остатков перед submit — обсуждается отдельно, может появиться позже как оптимизация UX, но не заменяет серверный envelope.
* Bulk-endpoint `POST /api/v1/operations/{id}/validate` — отдельная задача.
* Изменение legacy Django SSR формы операций (`templates/operations/form.html`, `static/js/operations_create.js`).
* Локализация / i18n новых строк UI.
* Метрики, аудит, трейсинг — `trace_id` уже включается в envelope, но отдельной инфраструктуры трассировки не делаем.
* Изменения в `corrections_service.py:912` (`correction_insufficient_balance`) — прецедент остаётся, миграция на новый формат возможна отдельным TZ, если будет запрос.

## 8. Тесты (минимальный набор)

Серверные (TZ 1):

* одна строка с недостаточным остатком → `insufficient_stock` с `operation_line_ids: ["line-1"]`;
* несколько разных дефицитных ТМЦ → `errors[]` содержит все;
* две строки одного item, которые превышают остаток только суммарно → `operation_line_ids` содержит обе строки, `required_qty` — сумма;
* точные `Decimal`-количества — без `float`-артефактов;
* `stale_version` — `expected_version` / `actual_version` в envelope;
* `operation_in_wrong_state` — `current_state` / `allowed_states[]`;
* отсутствие прав — `role_not_permitted` со статусом 403;
* `temporary_item_blocked` — после подтверждения правила в `Functional and WorkLogik.md`;
* rollback: после неудачного submit движения остатков не создаются (проверка `asset_register` до/после);
* порядок ошибок соответствует порядку строк операции;
* повторный submit после исправления проходит успешно;
* старый клиент по-прежнему может прочитать `detail` как строку.

UI (TZ 2):

* парсер корректно маппит envelope в модель, в т.ч. для `errors: []`;
* неизвестный код не ломает рендер;
* `operation_line_ids: ["line-1", "line-4"]` подсвечивает обе строки;
* toast отображает правильное число строк;
* скролл и фокус идут на первую проблемную строку;
* после изменения строки её ошибка очищается;
* перед новым submit все ошибки сбрасываются;
* a11y: `aria-invalid` и текстовая подсказка присутствуют.

## 10. Стратегия миграции (для ADR)

1. Этап 1 (TZ 1 + TZ 2): сервер возвращает новый формат параллельно со строкой `detail`. Старый клиент продолжает работать.
2. Этап 2: фронт мигрирует на парсер envelope (TZ 2). После успешного релиза текст в `detail` можно начинать сокращать, но не убирать полностью — нужна ещё одна итерация наблюдения.
3. Этап 3 (отдельный TZ, не в этой итерации): миграция `corrections_service.py:912` на тот же envelope; возможно, `detail` для submit-ошибок становится ссылочным/коротким.

## 11. Success Criteria

1. На dev-стенде при submit операции с нехваткой одной ТМЦ кладовщик видит toast «Не удалось провести: ошибка в 1 строке», строка подсвечена, рядом написано «На складе: X ед., запрошено: Y ед.», фокус и скролл на эту строку.
2. При submit с двумя строками одного кабеля (по 60 м, остаток 80 м) — toast «ошибки в 2 строках», обе строки подсвечены одним сообщением «На складе: 80 м, запрошено: 120 м».
3. После исправления одной из строк и повторного submit без нового GET остатков — операция проводится успешно.
4. Все остальные submit-ошибки (`stale_version`, `operation_in_wrong_state`, `role_not_permitted`) показываются в том же UX-паттерне (toast + детали), без inline-привязки там, где её быть не должно.
5. Старый клиент (или curl) видит человекочитаемый `detail` без потери информации.
6. `python -m pytest` SyncServer проходит; новые тесты из раздела 8 в комплекте.
