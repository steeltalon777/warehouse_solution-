# Экран «Операции»: пользовательские сценарии и acceptance-база

> Документ предназначен для двух целей:
>
> 1. Быть семантической базой для Playwright UI/acceptance-тестов.
> 2. Быть основой пользовательского руководства для сотрудников, которые могут не иметь глубокого опыта складского учёта.

---

## 1. Назначение экрана

Экран **«Операции»** — это основной журнал складских документов.

Через него пользователь должен понимать:

- какие операции были созданы;
- какие операции ещё являются черновиками;
- какие операции ожидают приёмки;
- какие операции уже проведены;
- какие операции отменены;
- кто создал операцию;
- откуда и куда движется имущество;
- какие действия доступны пользователю по его роли и текущему статусу операции.

Операция — это документ движения ТМЦ. Она может описывать приход, расход, перемещение, списание, выдачу, возврат выдачи или корректировку.

Ключевой принцип: **черновик операции сам по себе не меняет остатки и не является финальным бизнес-событием**.

Окончательное решение по правам, статусам и бизнес-правилам принимает SyncServer. UI может скрывать или блокировать кнопки, но не должен считаться источником истины.

---

## 2. Основная бизнес-логика черновиков и подтверждения

### 2.1 Черновик

Черновик операции может создать любой авторизованный пользователь, если интерфейс роли допускает доступ к созданию операции.

Черновик:

- не меняет остатки;
- не создаёт финального движения ТМЦ;
- не считается проведённой операцией;
- может быть отредактирован до подтверждения;
- может быть отменён до подтверждения;
- проходит полноценную проверку прав только на этапе submit / подтверждения.

### 2.2 Submit / подтверждение

Проверка складских прав выполняется на этапе **submit / подтверждения операции**.

Правило:

- кладовщик может подтвердить операцию только по своему складу / своим складам;
- главный кладовщик может подтвердить операцию по любому складу;
- root может подтвердить операцию по любому складу;
- обозреватель не может подтверждать операции.

Если прав нет, операция остаётся черновиком, а пользователь получает понятную ошибку.

Рекомендуемый текст ошибки:

```text
Нет прав на подтверждение операции по выбранному складу.
```

---

## 3. Основные роли на экране операций

## 3.1 Root

Root может:

- видеть все операции;
- создавать любые черновики;
- редактировать допустимые черновики;
- подтверждать операции по любым складам;
- отменять операции по любым складам в рамках доменных правил;
- скачивать документы;
- выполнять экспорт;
- видеть технические и административные действия, если они предусмотрены.

## 3.2 Главный кладовщик

Главный кладовщик может:

- видеть все операции;
- создавать любые черновики;
- подтверждать операции по любым складам;
- отменять операции в рамках бизнес-правил;
- работать с приёмкой по всем складам;
- скачивать документы;
- выполнять экспорт.

## 3.3 Кладовщик

Кладовщик может:

- видеть операции;
- создавать черновики операций;
- подтверждать операции только по своему складу / складам;
- редактировать свои неподтверждённые черновики;
- отменять свои неподтверждённые черновики;
- работать с приёмкой по своему складу.

## 3.4 Обозреватель

Обозреватель может:

- видеть операции;
- открывать карточку операции;
- искать, фильтровать и сортировать;
- просматривать документы, если это разрешено бизнес-логикой.

Обозреватель не может:

- подтверждать операции;
- отменять операции;
- редактировать операции;
- выполнять действия, меняющие складские данные.

> Решение для MVP: обозреватель только смотрит. Создание черновиков для обозревателя лучше не включать, чтобы журнал не превращался в кладбище случайных черновиков.

---

## 4. Элементы экрана

На экране **«Операции»** должны быть:

- заголовок «Операции»;
- краткое описание страницы;
- кнопка «Создать операцию»;
- кнопка «Приёмка»;
- кнопка «Экспорт»;
- строка поиска;
- фильтр по типу операции;
- фильтр по участку;
- фильтр по дате начала периода;
- фильтр по дате конца периода;
- чекбокс «Только мои»;
- кнопка «Сбросить»;
- вкладки статусов;
- таблица операций;
- пагинация;
- выбор количества строк на странице.

В таблице операций должны отображаться:

- номер операции;
- тип операции;
- статус;
- направление;
- количество позиций;
- автор;
- дата;
- доступные действия.

---

## 5. Вкладки журнала

## 5.1 Все

Показывает все операции, доступные текущему пользователю.

## 5.2 Черновики

Показывает операции, которые ещё не подтверждены и не влияют на остатки.

## 5.3 Ожидают приёмки

Показывает операции, для которых требуется физическая приёмка имущества.

Обычно сюда попадают:

- приход;
- перемещение.

## 5.4 Проведённые

Показывает операции, которые завершили свой бизнес-сценарий и уже повлияли на остатки или связанные репозитории.

## 5.5 Отменённые

Показывает операции, которые были отменены.

Отменённая операция не должна менять остатки. Если операция уже была проведена, отмена должна выполняться по отдельному доменному правилу.

---

# 6. Базовые пользовательские сценарии

## OPS-SCREEN-001: Пользователь открывает экран операций

**Дано:** пользователь вошёл в систему.

**Когда:** пользователь нажимает пункт меню «Операции».

**Тогда:** открывается журнал операций.

Пользователь видит:

- заголовок;
- поиск;
- фильтры;
- вкладки;
- таблицу;
- пагинацию;
- доступные действия.

### Acceptance checklist

```text
Проверить:
- страница загрузилась без ошибки;
- заголовок «Операции» виден;
- поле поиска доступно;
- таблица операций видна;
- пагинация видна;
- нет бесконечного loader;
- нет JS-ошибок, блокирующих работу страницы.
```

---

## OPS-SCREEN-002: В журнале нет операций

**Дано:** операций нет или фильтры ничего не нашли.

**Когда:** пользователь открывает экран или применяет фильтры.

**Тогда:** отображается понятное сообщение.

Рекомендуемый текст:

```text
Операции не найдены.
Попробуйте изменить фильтры или создать новую операцию.
```

### Acceptance checklist

```text
Проверить:
- нет ошибки 500;
- нет пустой белой таблицы без объяснения;
- empty-state виден;
- кнопка «Сбросить» работает, если применены фильтры;
- кнопка «Создать операцию» видна только ролям, которым она разрешена.
```

---

## OPS-SCREEN-003: Пользователь ищет операцию по номеру

**Дано:** в журнале есть операция с известным номером.

**Когда:** пользователь вводит полный номер или часть номера в поиск.

**Тогда:** таблица показывает подходящие операции.

Правила поиска:

- поиск работает по полному номеру;
- поиск работает по части номера;
- пробелы в начале и конце игнорируются;
- поиск не зависит от регистра.

### Acceptance checklist

```text
Ввести часть номера операции.
Проверить, что таблица отфильтрована.
Очистить поиск.
Проверить, что исходный список вернулся.
```

---

## OPS-SCREEN-004: Пользователь ищет по ТМЦ, SKU или хештегу

**Дано:** операция содержит конкретную ТМЦ, SKU или хештег.

**Когда:** пользователь вводит название ТМЦ, SKU или хештег.

**Тогда:** журнал показывает операции, где есть эта ТМЦ.

Этот сценарий важен, потому что пользователь часто помнит предмет, но не помнит номер документа.

---

## OPS-SCREEN-005: Пользователь фильтрует операции по типу

**Дано:** в журнале есть операции разных типов.

**Когда:** пользователь выбирает тип операции.

**Тогда:** таблица показывает только операции выбранного типа.

Типы операций:

- приход;
- расход;
- перемещение;
- списание;
- выдача;
- возврат выдачи;
- корректировка.

### Acceptance checklist

```text
Выбрать «Приход».
Проверить, что в колонке «Тип» только приход.
Выбрать «Перемещение».
Проверить, что отображаются только перемещения.
Сбросить фильтр.
Проверить, что снова отображаются разные типы операций.
```

---

## OPS-SCREEN-006: Пользователь фильтрует операции по участку

**Дано:** есть операции по разным участкам.

**Когда:** пользователь выбирает участок.

**Тогда:** таблица показывает операции, связанные с этим участком.

Для операций с двумя складами, например перемещения, операция должна попадать в фильтр, если выбранный участок является:

- складом-отправителем;
- складом-получателем.

---

## OPS-SCREEN-007: Пользователь фильтрует операции по периоду

**Дано:** операции созданы в разные даты.

**Когда:** пользователь выбирает дату начала и дату конца периода.

**Тогда:** таблица показывает операции только за выбранный период.

Пограничные проверки:

- указана только дата начала;
- указана только дата конца;
- дата начала больше даты конца;
- пустой период;
- сегодняшняя дата;
- операции на границе дня.

Рекомендуемый текст ошибки:

```text
Дата начала не может быть позже даты окончания.
```

---

## OPS-SCREEN-008: Пользователь включает «Только мои»

**Дано:** в журнале есть операции разных авторов.

**Когда:** пользователь ставит галочку «Только мои».

**Тогда:** таблица показывает только операции, созданные текущим пользователем.

---

## OPS-SCREEN-009: Пользователь сбрасывает фильтры

**Дано:** включены поиск, тип, участок, даты и «Только мои».

**Когда:** пользователь нажимает «Сбросить».

**Тогда:** все фильтры очищаются, таблица возвращается к состоянию по умолчанию.

### Acceptance checklist

```text
Заполнить все фильтры.
Нажать «Сбросить».
Проверить:
- поиск пустой;
- тип = все типы;
- участок = все участки;
- даты пустые;
- чекбокс «Только мои» снят;
- таблица обновилась.
```

# 7. Сценарии создания операций

## OPS-CREATE-001: Пользователь нажимает «Создать операцию»

**Дано:** пользователь находится в журнале операций.

**Когда:** пользователь нажимает «Создать операцию».

**Тогда:** открывается форма создания операции.

Форма должна позволять указать:

- тип операции;
- склад-источник, если нужен;
- склад-получатель, если нужен;
- ТМЦ;
- количество;
- комментарий.

Операция сначала создаётся как черновик.

---

## OPS-CREATE-002: Создание черновика прихода

**Дано:** пользователь создаёт приход.

**Когда:** пользователь выбирает склад, добавляет строки ТМЦ и сохраняет.

**Тогда:** создаётся черновик прихода.

Ожидаемый результат:

- статус «Черновик»;
- операция появляется во вкладке «Черновики»;
- остатки не меняются;
- доступны действия редактирования и отмены.

---

## OPS-CREATE-003: Создание черновика расхода

**Дано:** пользователь создаёт расход.

**Когда:** пользователь выбирает склад, добавляет ТМЦ и количество.

**Тогда:** создаётся черновик расхода.

Важно:

- на этапе черновика можно не блокировать чужой склад;
- на этапе submit сервер проверит, имеет ли пользователь право проводить расход с выбранного склада.

---

## OPS-CREATE-004: Создание черновика перемещения

**Дано:** пользователь создаёт перемещение.

**Когда:** пользователь выбирает склад-отправитель, склад-получатель и добавляет ТМЦ.

**Тогда:** создаётся черновик перемещения.

Проверки:

- склад-отправитель обязателен;
- склад-получатель обязателен;
- склады не должны совпадать;
- строки ТМЦ обязательны;
- количество должно быть больше нуля.

---

## OPS-CREATE-005: Создание черновика списания

**Дано:** пользователь создаёт списание.

**Когда:** пользователь выбирает склад, ТМЦ, количество и причину.

**Тогда:** создаётся черновик списания.

Причина списания должна быть обязательной.

---

## OPS-CREATE-006: Создание черновика выдачи

**Дано:** пользователь выдаёт имущество человеку, машине, базе или другому объекту.

**Когда:** пользователь выбирает склад, объект выдачи, ТМЦ и количество.

**Тогда:** создаётся черновик выдачи.

До submit:

- ТМЦ ещё не списывается со склада;
- ТМЦ ещё не закрепляется за объектом.

После submit:

- складской остаток уменьшается;
- ТМЦ появляется в репозитории выдачи;
- ТМЦ закрепляется за объектом выдачи.

---

## OPS-CREATE-007: Создание черновика возврата выдачи

**Дано:** за объектом числится имущество.

**Когда:** пользователь выбирает объект, имущество и склад возврата.

**Тогда:** создаётся черновик возврата выдачи.

После submit:

- ТМЦ снимается с объекта;
- ТМЦ возвращается на выбранный склад.

---

## OPS-CREATE-008: Создание черновика корректировки

**Дано:** пользователь создаёт корректировку.

**Когда:** пользователь выбирает склад, ТМЦ, новое количество и причину.

**Тогда:** создаётся черновик корректировки.

Рекомендация:

- создать черновик может кладовщик;
- submit корректировки лучше разрешить только root и главному кладовщику.

Корректировка должна быть отдельной операцией, а не прямой правкой остатка.

---

# 8. Сценарии редактирования черновика

## OPS-DRAFT-001: Автор редактирует свой черновик

**Дано:** пользователь создал черновик.

**Когда:** пользователь открывает его и меняет данные.

**Тогда:** изменения сохраняются.

Можно менять:

- комментарий;
- склад, если операция ещё черновик;
- строки ТМЦ;
- количество.

Рекомендация: тип операции после создания лучше не менять.

---

## OPS-DRAFT-002: Пользователь добавляет строку ТМЦ

**Дано:** открыт черновик.

**Когда:** пользователь ищет ТМЦ и добавляет строку.

**Тогда:** строка появляется в таблице операции.

Проверки:

- поиск работает по названию;
- поиск работает по SKU;
- категория отображается;
- единица измерения отображается;
- количество валидируется.

---

## OPS-DRAFT-003: Пользователь удаляет строку ТМЦ

**Дано:** в черновике есть несколько строк.

**Когда:** пользователь удаляет строку.

**Тогда:** строка исчезает из черновика.

Если это последняя строка, submit должен быть невозможен.

---

## OPS-DRAFT-004: Пользователь указывает неправильное количество

Неверные значения:

- `0`;
- `-1`;
- пустое значение;
- буквы;
- слишком большое число;
- число с неправильным разделителем.

Ожидаемый результат:

- UI показывает ошибку;
- submit заблокирован;
- сервер также отклоняет запрос, если UI пропустил ошибочные данные.

---

## OPS-DRAFT-005: Пользователь открывает чужой черновик

Рекомендованное поведение:

- root может редактировать чужие черновики;
- главный кладовщик может редактировать чужие черновики;
- кладовщик может смотреть чужие черновики, но редактировать только свои;
- обозреватель только смотрит.

### Acceptance checklist

```text
Создать черновик пользователем А.
Войти пользователем Б.
Открыть черновик.
Проверить набор доступных действий.
```

# 9. Сценарии submit / подтверждения

## OPS-SUBMIT-001: Кладовщик подтверждает операцию своего склада

**Дано:** кладовщик создал черновик операции по своему складу.

**Когда:** кладовщик нажимает «Подтвердить».

**Тогда:** SyncServer принимает submit.

Ожидаемый результат:

- статус меняется;
- черновик перестаёт быть редактируемым;
- создаётся PDF-документ, если он предусмотрен;
- остатки меняются или создаётся приёмка, в зависимости от типа операции.

---

## OPS-SUBMIT-002: Кладовщик пытается подтвердить операцию чужого склада

**Дано:** кладовщик создал черновик операции по чужому складу.

**Когда:** кладовщик нажимает «Подтвердить».

**Тогда:** сервер отклоняет submit.

Ожидаемый результат:

- операция остаётся черновиком;
- UI показывает ошибку прав;
- остатки не меняются;
- документы не создаются как финальные.

Рекомендуемый текст ошибки:

```text
Нет прав на подтверждение операции по выбранному складу.
```

### Acceptance checklist

```text
Создать черновик с чужим складом.
Нажать submit.
Ожидать ошибку 403 или доменную ошибку.
Проверить, что статус остался «Черновик».
```

---

## OPS-SUBMIT-003: Главный кладовщик подтверждает операцию любого склада

**Дано:** есть черновик по любому складу.

**Когда:** главный кладовщик нажимает «Подтвердить».

**Тогда:** операция подтверждается.

---

## OPS-SUBMIT-004: Root подтверждает операцию любого склада

**Дано:** есть черновик по любому складу.

**Когда:** root нажимает «Подтвердить».

**Тогда:** операция подтверждается.

---

## OPS-SUBMIT-005: Обозреватель пытается подтвердить операцию

**Дано:** обозреватель открыл черновик.

**Когда:** пользователь смотрит доступные действия.

**Тогда:** кнопка submit скрыта или недоступна.

Если запрос отправлен напрямую, сервер должен вернуть отказ.

# 10. Сценарии по типам операций после submit

## OPS-FLOW-RECEIVE-001: Приход с полной приёмкой

**Дано:** создан черновик прихода.

**Когда:** пользователь с правами подтверждает операцию.

**Тогда:** операция попадает в приёмку.

После приёмки:

- принятое количество зачисляется на склад;
- операция становится проведённой;
- документ доступен для скачивания.

---

## OPS-FLOW-RECEIVE-002: Приход с частичной приёмкой

**Дано:** в приходе указано 10 единиц.

**Когда:** приёмщик принимает 7, а 3 отмечает как непринятое.

**Тогда:**

- 7 зачисляется на склад;
- 3 попадает в репозиторий непринятого;
- операция получает статус частичной приёмки или проведённой с расхождением.

---

## OPS-FLOW-MOVE-001: Перемещение с полной приёмкой

**Дано:** склад А отправляет на склад Б 5 единиц.

**Когда:** операция подтверждена и склад Б принимает все 5.

**Тогда:**

- со склада А имущество убывает;
- на склад Б имущество прибывает;
- операция становится проведённой.

Важно: точное время изменения остатков при перемещении должно быть отдельно зафиксировано в доменной логике.

Возможные варианты:

- списание со склада-отправителя происходит на submit, приход на склад-получатель — после приёмки;
- оба движения происходят после приёмки;
- используется отдельное состояние «в пути».

---

## OPS-FLOW-MOVE-002: Перемещение с частичной приёмкой

**Дано:** со склада А отправлено 5 единиц.

**Когда:** склад Б принимает 3, а 2 не приехали.

**Тогда:**

- 3 зачисляются на склад Б;
- 2 попадают в репозиторий непринятого;
- в карточке операции видно расхождение.

---

## OPS-FLOW-ISSUE-001: Выдача имущества

**Дано:** на складе есть ТМЦ.

**Когда:** операция выдачи подтверждена.

**Тогда:**

- остаток склада уменьшается;
- ТМЦ появляется в репозитории выдачи;
- ТМЦ закрепляется за объектом: человеком, машиной, базой или другим объектом.

---

## OPS-FLOW-ISSUE-RETURN-001: Возврат выданного имущества

**Дано:** за объектом числится ТМЦ.

**Когда:** подтверждён возврат выдачи.

**Тогда:**

- ТМЦ снимается с объекта;
- ТМЦ возвращается на выбранный склад;
- история выдачи сохраняется.

---

## OPS-FLOW-WRITEOFF-001: Списание со склада

**Дано:** на складе есть ТМЦ.

**Когда:** списание подтверждено.

**Тогда:**

- остаток уменьшается;
- в истории операции указана причина списания;
- документ списания доступен.

---

## OPS-FLOW-WRITEOFF-002: Списание с объекта выдачи

**Дано:** ТМЦ числится за человеком, машиной, базой или другим объектом.

**Когда:** создаётся и подтверждается списание.

**Тогда:**

- ТМЦ снимается с объекта;
- ТМЦ не возвращается на склад;
- в истории объекта видно списание.

---

## OPS-FLOW-ADJUST-001: Корректировка остатка

**Дано:** остаток по ТМЦ отличается от фактического.

**Когда:** создаётся и подтверждается корректировка.

**Тогда:**

- создаётся операция корректировки;
- остаток меняется;
- в истории видна причина;
- старые операции не переписываются.

---

# 11. Сценарии отмены

## OPS-CANCEL-001: Автор отменяет свой черновик

**Дано:** пользователь создал черновик.

**Когда:** пользователь нажимает «Отменить».

**Тогда:** операция получает статус «Отменена».

Остатки не меняются.

---

## OPS-CANCEL-002: Кладовщик пытается отменить чужой черновик

**Дано:** черновик создан другим пользователем.

**Когда:** кладовщик пытается отменить черновик.

**Тогда:** действие запрещено.

---

## OPS-CANCEL-003: Главный кладовщик отменяет черновик или неподтверждённую операцию

**Дано:** операция ещё не проведена.

**Когда:** главный кладовщик отменяет её.

**Тогда:** операция получает статус «Отменена».

---

## OPS-CANCEL-004: Root отменяет подтверждённую операцию

**Дано:** операция уже подтверждена.

**Когда:** root отменяет операцию.

**Тогда:** система выполняет доменное правило отмены.

Варианты доменного правила:

- операция отменяется с обратным движением;
- создаётся отдельная сторно-операция;
- отмена запрещена, если уже есть приёмка;
- отмена разрешена только до определённого статуса.

Это правило должно быть отдельно зафиксировано перед полной автоматизацией тестов.

# 12. Действия в таблице операций

На строке операции могут быть доступны действия:

- открыть / посмотреть;
- редактировать;
- подтвердить;
- отменить;
- скачать PDF;
- распечатать;
- удалить / архивировать, если это разрешено.

## OPS-ACTION-001: Открыть карточку операции

**Когда:** пользователь нажимает номер операции или иконку просмотра.

**Тогда:** открывается карточка операции.

Карточка показывает:

- номер;
- тип;
- статус;
- направление;
- автора;
- дату создания;
- строки ТМЦ;
- комментарий;
- историю действий;
- документы;
- доступные кнопки.

---

## OPS-ACTION-002: Редактировать операцию

Редактирование доступно только для черновиков или неподтверждённых операций.

Если операция проведена:

- кнопка редактирования скрыта;
- или открывается только просмотр;
- сервер отклоняет PATCH-запрос.

---

## OPS-ACTION-003: Скачать PDF

**Дано:** операция подтверждена или проведена.

**Когда:** пользователь нажимает PDF / печать.

**Тогда:** скачивается документ.

Для черновика:

- PDF недоступен;
- либо формируется предварительная версия с явной пометкой «Черновик».

Рекомендация для MVP: PDF формируется только после submit.

---

## OPS-ACTION-004: Экспорт журнала

**Дано:** пользователь применил фильтры.

**Когда:** пользователь нажимает «Экспорт».

**Тогда:** выгружается список операций с учётом текущих фильтров.

Экспорт должен учитывать:

- поиск;
- тип;
- участок;
- период;
- «Только мои»;
- текущую роль пользователя.

# 13. Негативные и пограничные сценарии

## OPS-EDGE-001: Двойной submit

**Дано:** пользователь нажал «Подтвердить» два раза.

**Тогда:** операция подтверждается один раз.

Ожидаемый результат:

- кнопка блокируется после первого нажатия;
- повторный запрос не создаёт дубль;
- UI показывает один итоговый статус.

---

## OPS-EDGE-002: Два пользователя открыли один черновик

**Дано:** пользователь А и пользователь Б открыли один черновик.

**Когда:** пользователь А подтверждает операцию, а пользователь Б пытается редактировать.

**Тогда:** пользователь Б получает сообщение:

```text
Операция уже изменила статус. Обновите страницу.
```

---

## OPS-EDGE-003: Операция исчезла или изменилась после открытия

**Дано:** пользователь открыл карточку операции.

**Когда:** операция была отменена, изменена или архивирована другим пользователем.

**Тогда:** UI показывает понятное сообщение и не падает.

---

## OPS-EDGE-004: Нет связи с SyncServer

**Дано:** SyncServer недоступен.

**Когда:** пользователь открывает операции или нажимает действие.

**Тогда:** UI показывает ошибку:

```text
Сервер склада временно недоступен. Попробуйте позже.
```

---

## OPS-EDGE-005: Пользователь потерял права между открытием и submit

**Дано:** пользователь открыл черновик, когда права были.

**Когда:** root изменил доступы пользователя, и пользователь нажал submit.

**Тогда:** сервер отклоняет действие, UI показывает ошибку прав.

---

## OPS-EDGE-006: В операции ТМЦ стала неактивной

**Дано:** черновик содержит ТМЦ, которую потом деактивировали.

**Когда:** пользователь пытается подтвердить операцию.

**Тогда:** сервер применяет одно из доменных правил:

- разрешает submit, если ТМЦ уже была добавлена в черновик;
- запрещает submit с понятной ошибкой.

Рекомендация: разрешать уже добавленную ТМЦ, но запрещать добавление неактивной ТМЦ в новые строки.

---

## OPS-EDGE-007: Недостаточно остатка

**Дано:** в расходе, перемещении, выдаче или списании указано больше, чем есть на складе.

**Когда:** пользователь нажимает submit.

**Тогда:** сервер отклоняет операцию.

Рекомендуемый текст ошибки:

```text
Недостаточно остатка на складе.
```

---

## OPS-EDGE-008: Совпадают склад-отправитель и склад-получатель

**Дано:** пользователь создаёт перемещение.

**Когда:** пользователь выбирает один и тот же склад отправителем и получателем.

**Тогда:** операция не подтверждается.

Рекомендуемый текст ошибки:

```text
Склад-отправитель и склад-получатель не должны совпадать.
```

---

## OPS-EDGE-009: Пустой черновик

**Дано:** операция не содержит строк ТМЦ.

**Когда:** пользователь нажимает submit.

**Тогда:** submit запрещён.

---

## OPS-EDGE-010: Некорректный диапазон дат в фильтре

**Дано:** дата начала позже даты окончания.

**Когда:** пользователь применяет фильтр.

**Тогда:** UI показывает ошибку и не отправляет бессмысленный запрос.

# 16. Нерешённые доменные правила

Эти пункты нужно отдельно зафиксировать перед полной автоматизацией acceptance-тестов.

## 16.1 Обозреватель и черновики

Нужно решить:

- обозреватель может создавать черновики;
- или обозреватель только просматривает операции.

Рекомендация для MVP: обозреватель только просматривает.

## 16.2 Момент изменения остатков при перемещении

Нужно выбрать правило:

- списание со склада-отправителя на submit, приход на склад-получатель после приёмки;
- оба движения после приёмки;
- используется состояние «в пути».

## 16.3 Редактирование чужих черновиков

Нужно выбрать правило:

- root/chief могут редактировать чужие черновики;
- кладовщик редактирует только свои;
- кладовщик может редактировать черновики своего склада.

Рекомендация: root/chief могут редактировать чужие, кладовщик только свои.

## 16.4 Удаление операций

Рекомендация:

- физически не удалять операции;
- использовать статусы `cancelled` / `archived`;
- сохранять историю действий.

## 16.5 Отмена проведённой операции

Нужно выбрать правило:

- root может отменить напрямую;
- создаётся сторно-операция;
- отмена запрещена после приёмки;
- отмена разрешена только до определённого статуса.

## 16.6 PDF для черновика

Нужно выбрать правило:

- PDF доступен только после submit;
- или черновик может иметь предварительный PDF с пометкой «Черновик».

Рекомендация для MVP: PDF только после submit.

## 16.7 Подтверждение корректировки

Нужно выбрать правило:

- кладовщик может подтвердить корректировку по своему складу;
- или корректировку подтверждают только root/chief.

Рекомендация: submit корректировки только root/chief.

# 17. Краткая пользовательская памятка

## Что такое операция

Операция — это документ, который описывает движение имущества на складе.

## Что такое черновик

Черновик — это подготовленный документ. Он ещё ничего не меняет в остатках.

## Когда операция становится настоящей

Операция становится бизнес-действием после подтверждения.

## Почему я могу создать черновик, но не могу подтвердить

Создать черновик можно заранее. Но подтвердить операцию может только пользователь с правами на нужный склад.

## Почему операция ожидает приёмки

Приход и перемещение требуют физической проверки имущества. Пока имущество не принято, операция может ожидать приёмки.

## Что делать, если приехало не всё

При приёмке нужно указать, сколько фактически принято. Непринятое имущество попадёт в отдельный репозиторий непринятого.

## Что делать, если ошибся

Если операция ещё черновик, её можно отредактировать или отменить. Если операция уже подтверждена, действия зависят от роли пользователя и доменных правил.
