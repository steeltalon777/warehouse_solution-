## 2. IntegrityError при создании пользователя — sync_user_token NOT NULL

**Симптом:** при создании пользователя через админку Django:
```
django.db.utils.IntegrityError: null value in column "sync_user_token"
of relation "users_syncuserbinding" violates not-null constraint
```

**Причина:** Django-миграция `users/0007_make_optional_string_fields_nullable` не была применена на проде. Модель в коде определяет поле как `null=True`, но в БД колонка всё ещё `NOT NULL`.

**Исправление (когда будет команда):**
```bash
ssh makc@147.45.102.135
docker exec warehouse_web python manage.py migrate users
```

**Затронутые файлы:**
- `Warehouse_web/apps/users/migrations/0007_make_optional_string_fields_nullable.py` — миграция, которая делает `sync_user_token` nullable
- `Warehouse_web/apps/users/models.py:94` — `SyncUserBinding.sync_user_token`

**Статус:** выполнено на проде — применены `users.0007` и `users.0008`

## 5. В форму операции иногда попадают неактуальные остатки

**Симптом:** при создании/редактировании операции в форме местами отображаются/используются устаревшие остатки.

**Ожидаемое поведение:** форма показывает актуальные остатки для выбранного склада/ТМЦ; перед submit SyncServer всё равно выполняет авторитетную проверку остатков и прав.

**Тип:** баг/UX + интеграционные проверки на стенде

**Статус:** **mitigation в 3.0.1** (2026-06-16). Полное решение отложено в 3.1.

### Mitigation (3.0.1)

**Что сделано (Angular):**
1. Добавлен `private balanceRefreshSeq = 0` — монотонно возрастающий счётчик для sequencing запросов балансов
2. Эффект refresh балансов захватывает `seq = ++this.balanceRefreshSeq`; после `await` проверяет `seq !== this.balanceRefreshSeq` и `relevantSiteId() === siteId` перед применением
3. Добавлены helper-методы: `shouldUseWarehouseBalances()`, `refreshBeforePersist()`
4. `onSave()` и `onSubmit()` теперь `async` и вызывают `await this.refreshBeforePersist()` перед emit
5. Object-source flows (ISSUE_RETURN, WRITE_OFF с объектом, prefilled asset lines) не затронуты

**Изменённый файл:**
- `Warehouse_frontend/src/app/features/operations/components/operation-create-modal/operation-create-modal.component.ts`

**Что сделано (SyncServer — регрессионные тесты):**
- Добавлены 2 теста `test_stale_balance_conflict.py`:
  - EXPENSE: submit с исчерпанным балансом → 409 Conflict
  - MOVE: submit с исчерпанным source-балансом → 409 Conflict
- Тесты используют реальную БД (через session_factory) и API (через AsyncClient)
- Документировано: SyncServer остаётся авторитетным источником проверки остатков

## 7. Логирование SyncServer: request/response вместо SQL-шума

**Симптом:** сейчас в логах SyncServer слишком много SQL-шума, а для эксплуатации нужны аккуратные записи уровня request/response; подробный traceback нужен только для 5xx/ошибок.

**Ожидаемое поведение:**
- на каждый HTTP-запрос: method, path, status_code, duration_ms, request_id, user/device/site если известно;
- SQL-логи по умолчанию выключены или сильно приглушены;
- 4xx пишутся компактно;
- 5xx пишутся с exception и traceback;
- секреты/токены никогда не попадают в лог.

**Тип:** инфраструктурный патч + проверка логов на стенде

**Статус:** **исправлено в 3.0.1** (2026-06-16)

### Исправление (3.0.1)

**C1 — Access logging middleware:**

В `main.py` middleware переименован в `access_log_middleware` и добавлено структурированное access-логирование:

```
event: "http_request"
method, path, status_code, duration_ms (rounded 1d), request_id
```

Уровни:
- 2xx/3xx: `logger.info`
- 4xx: `logger.warning` (без traceback)
- 5xx/unhandled: `logger.error` с `exc_info=True`

Запрещённые поля не логируются: request body, response body, токены, cookies, request.headers целиком.

`X-Request-Id` проставляется на все ответы, включая handled 500.

**C2 — SQL logging control:**

- В `config.py` добавлено поле `LOG_SQL: bool = False`
- В `db.py` изменено с `echo=settings.APP_ENV == "dev"` на `echo=settings.LOG_SQL`
- `sqlalchemy.engine` остаётся на WARNING по умолчанию
- `LOG_SQL=1|true|yes|on` включает SQL echo явно

**Изменённые файлы:**
- `SyncServer/main.py`
- `SyncServer/app/core/config.py`
- `SyncServer/app/core/db.py`

**Верификация на стенде:**
- Health-запрос логируется с `event=http_request`, `duration_ms`, `request_id`, `status_code`
- В логах отсутствуют SQL-запросы, токены, request.body
- `make status` — полная проверка здоровья стенда

- связь с `Warehouse_client_core` и будущими desktop/mobile клиентами;
- как это связано с аудитом и логинами;
- не превращать Django в источник истины по offline-сессиям.

**Где копать:**

- `SyncServer/app/api/routes_auth.py` / `/auth/context` если есть
- `SyncServer/app/models/` и миграции Alembic
