## 1. Контекст и проблема

### 1.1. Текущее состояние

Продакшен-шаблон накладной `warehouse-waybill-ru@2.1.0` (Typst, QDE)
утверждён пользователем по составу подписей (обзор 03.09.2026):
подписи только на последней странице; наборы: MOVE → Водитель + Груз
принял; ISSUE/ISSUE_RETURN/EXPENSE → Принял; WRITE_OFF → Списание
разрешил; остальные → только Кладовщик.

Пагинация в 2.1.0 (и 2.0.0) — точный порт legacy-алгоритма
(`Warehouse_web` `services.py paginate_waybill_lines`): страница
получает фиксированный бюджет в «row units» (MOVE: первая 23,
средние 29, последняя 22), строка стоит `visual_lines()` юнитов —
жадная эвристика переноса по числу символов
(`name-chars-per-visual-line: 40`), не связанная с реальным
лайаутом Typst.

### 1.2. Наблюдаемый дефект (замеры 05.09.2026, шаблон 2.1.0)

| Документ | Страниц | Строк на страницах |
|---|---|---|
| MOVE `WB-1-20260826-a66c` (69 позиций) | 4 | 15 / 19 / 15 / 20 |
| MOVE `WB-1-20260710-6eab` (143 позиции) | 8 | 16 / 21 / 23 / 24 / 17 / 17 / **6** / 19 |

Страницы заполнены неравномерно: страницы с длинными наименованиями
содержат меньше строк; жадный префикс + резерв последней страницы
оставляет «огрызок» (6 строк на стр. 7 у 6eab); на первой странице
a66c визуально помещается ещё ≥5 строк.

### 1.3. Требования пользователя (05.09.2026)

1. **Не наследовать методы legacy**: QDE не обязан воспроизводить
   legacy-пагинацию; цель — собственная качественная модель.
2. **Главный упор — балансировка строк**: равномерное заполнение
   страниц, без страниц-огрызков.
3. **Растяжение строк до заполнения — с ограничением**: высота строки
   меняется в пределах **±15% от нормальной**; недопустимо растягивать
   10 строк на всю страницу (на «пустых» страницах остаётся свободное
   место — это приемлемо).
4. **Шрифт — только фолбек**: уменьшение максимум на **1–2 пункта**
   (11 → 10 → 9pt) и только для наименований ТМЦ, занимающих
   **больше 2 нормальных строк**, чтобы уложить их в ≤2 строки.
5. Зафиксировать физические границы A4 книжной ориентации и
   отслеживать заполненность относительно них; альбомная ориентация —
   позже (геометрия должна быть единой точкой конфигурации).

## 3. Факты реализации, на которые опирается ТЗ (проверено 05.09.2026)

- Типовая структура пакета: `manifest.yaml` (id/version/entrypoint),
  `main.typ`, `layout-config.typ`, `components/pagination.typ`,
  `components/signatures.typ`, `LAYOUT.md` (см. пакет 2.1.0).
- Рендер-конвейер: `Warehouse_web` `render_via_qde()`
  (`apps/documents/services.py:882`) → `python -m qm_cli.main render`
  → `qm_engine` пишет полный конверт в `document.json` →
  `typst compile main.typ` c `--font-path`, `--ignore-system-fonts`,
  `--creation-timestamp` (пинн), `--root` во временном каталоге.
- Разрешение шаблонов: `QM_TEMPLATES_DIR` (в контейнере
  `/opt/qde/templates`) → `qm_engine.paths.default_templates_dir()`.
  Exit code 5 (`RENDER_FAILED`) — любая ошибка рендера, включая
  `panic` в Typst; маппинг ошибок в Django — по коду из
  JSON-диагностики в stderr (`_qde_error_from_stderr`,
  `services.py:970`), не по тексту сообщения.
- `measure(content)` работает внутри `#context` в Typst 0.15.1
  (проверено в контейнере `warehouse_web`); `page.height()` в 0.15
  отсутствует — геометрия листа задаётся и отслеживается самим
  шаблоном (он владелец `#set page`).
- Тесты: в `tests/unit/` нет Python-тестов самого `pagination.typ`;
  пагинация проверяется интеграционно через рендер:
  `tests/integration/test_canonical_waybill.py` пинает шаблон
  **2.0.0** (фикстуры `waybill-qde-{1,20,75,200,500}.typst.json`,
  `EXPECTED_PAGES = {1:1, 20:4, 75:10, 200:27, 500:66}`) и НЕ должен
  меняться (регрессия замороженной версии).
- Запуск тестов QDE на хосте:
  `QuartermasterDocumentEngine/.venv/bin/python -m pytest ...`
  (venv содержит pytest 9.1.1, pymupdf, pypdf, jsonschema, qm_engine
  в editable-режиме); бинарь typst резолвится движком из
  `QuartermasterDocumentEngine/.spike/typst-0.15.1/typst-x86_64-unknown-linux-musl/typst`
  (переменная `QM_TYPST_BINARY` не нужна). Стенд для тестов QDE не
  требуется.
- Контейнер `warehouse_web`: образ копирует
  `QuartermasterDocumentEngine/templates/warehouse-waybill-ru` в
  `/opt/qde/templates/warehouse-waybill-ru` целиком (все версии);
  в dev compose примонтирован только `./Warehouse_web:/app` —
  каталог QDE в контейнер попадает через `docker cp` либо ребилд
  образа.
- Настройки стенда: `DOCUMENTS_RENDER_MODE` по умолчанию `legacy`;
  QDE-рендер доступен через теневой путь независимо от режима
  (`render_shadow_pdf`).

## 4. Целевой дизайн `2.2.0`

Обязательные принципы:
- детерминизм: повторный рендер байт-идентичен (пиннованный
  timestamp, бандловые шрифты, детерминированный алгоритм — никаких
  случайных/время-зависимых веток);
- `Типст никогда не решает, где разрыв страницы`: сохраняется модель
  «одна страница = один `block(breakable: false)` + явный
  `pagebreak()`»;
- все клиентские параметры — только в `layout-config.typ`
  (правило LAYOUT.md §8); движок пагинации не содержит литералов
  ёмкостей/геометрии;
- футер-счётчик «Лист N из M» остаётся в зарезервированной области
  `#set page(footer: ...)` (инвариант LAYOUT.md §4).

### 4.1. Физические границы листа (новый блок конфигурации)

В `layout-config.typ` блок `page` сохраняется и дополняется явными
производными константами (единая точка правды для геометрии):

```typst
page: (
  size: "a4",
  orientation: "portrait",
  margin: (top: 16mm, right: 14mm, bottom: 14mm, left: 14mm),
),
page-geometry: (
  paper-width: 210mm,
  paper-height: 297mm,
  content-width: 182mm,   // = paper-width − left − right
  content-height: 267mm,  // = paper-height − top − bottom
),
```

Инвариант движка: при старте рендера проверить
`content-height == paper-height − margin.top − margin.bottom` и
`content-width == paper-width − margin.left − margin.right`;
при рассогласовании — `panic("page-geometry is inconsistent with page margins")`.
Это и есть «зафиксированные физические границы»: вся пагинация
считается от `content-height`, а не от эвристик.

Альбомная ориентация в будущем: смена `orientation` + двух чисел в
`page-geometry`; алгоритм не меняется.

### 4.2. Измерительный слой (заменяет символьную эвристику)

`main.typ` реструктурируется: нормализация → измерения → пагинация →
рендер выполняются внутри одного `#context { ... }` (проверено:
`measure()` доступен в `context` в Typst 0.15.1). Футер/счётчик не
затрагивается.

Измеряется (один раз за рендер), в реальных настройках таблицы
(DejaVu Sans 11pt, `top-edge: 0.582em`, `bottom-edge: -0.582em`,
`par(leading: 0pt)`, `inset: 2mm`, колонки `11mm / 1fr / 24mm / 28mm`):

1. **H1 — нормальная высота однострочной строки**: высота строки
   таблицы с эталонным коротким наименованием (например `"А"`).
   Ориентир ~8.5mm; значение берётся только из измерения.
2. **Высоты строк `h[i]`**: каждая строка измеряется как настоящая
   однорядная таблица с реальным содержимым (№/наименование/ед./кол-во),
   с `wrap_name()` (сохраняется — защита от сверхдлинных токенов).
3. **Хром по ролям**:
   - `HF` — блок заголовка первой страницы (титул 16pt + реквизиты,
     со всеми `block(spacing)` и `v()`);
   - `HM` — короткий титул 14pt средних/последней страниц (со
     spacing);
   - `HT` — строка-шапка таблицы (заголовочная строка с филлом);
   - `HS(op)` — блок подписей для типа операции (`v(8mm)` +
     Кладовщик + грид декларативных блоков; измеряется с реальной
     конфигурацией `operation-signature-sets`).

Доступные высоты для строк данных:

```
A_first  = content-height − HF − HT
A_middle = content-height − HM − HT
A_last   = content-height − HM − HT − HS(op)
A_single = content-height − HF − HT − HS(op)
```

`HS(op)` измеряется на реальном подписном контенте:
`measure(render_signature_section(true, config, blocks))` (контент
в Typst ленивый — измерение не рендерит его в документ).

Разделение ответственности: **`components/pagination.typ` остаётся
чистым** — не вызывает ни `measure()`, ни `json()`; получает
готовые высоты строк и площади ролей и возвращает распределение.
Все измерения живут в `main.typ` внутри `context`.

Ёмкости в юнитах (`page-rows`, `operation-last-rows`,
`operation-single-rows`) и `name-chars-per-visual-line` как параметр
оценки высоты **удаляются из конфигурации**. Параметр чанкинга
длинных токенов для `wrap_name()` сохраняется под именем
`max-token-chars: 40` (используется только в `wrap_name`).

### 4.3. Font-fallback (до паковки, построчно)

Конфигурация:

```typst
font-fallback: (
  max-lines: 2,            // порог: больше 2 нормальных строк
  sizes: (10pt, 9pt),      // шаги уменьшения от базовых 11pt
),
```

Для каждой строки: если измеренная `h[i] > max-lines × H1`,
переизмерить строку с размером шрифта ячейки наименования 10pt; если
всё ещё > 2×H1 — 9pt. Применяется первый размер, при котором высота
≤ `max-lines × H1`; если и 9pt не уложил — строка остаётся как есть
(её фактическая высота участвует в упаковке; без паники). Размер
шрифта — свойство строки: при рендере ячейки этой строки получают
соответствующий `text(size: ...)`. Другие ячейки строки не меняют
размер.

### 4.4. Упаковка и балансировка (ядро)

Вход: высоты `h[0..n−1]` (после §4.3), площади
`A_first/A_middle/A_last/A_single`. Строки не переупорядочиваются.
Модель страниц: `первая → средние × P → последняя`; последняя —
единственная страница с подписями.

```
1.  n == 0 → одна пустая страница (роль «первая») со строкой-заглушкой;
    растяжение (§4.5) к ней не применяется.
2.  Если существует h[i] > max(A_first, A_middle, A_last)
        → panic("Waybill line is too tall to fit on one page.")
3.  Если h[0] > A_first
        → panic("Waybill line is too tall for the first-page layout.")
    (первая строка обязана лечь на первую страницу — см. шаг 5а)
4.  n == 1 и h[0] > A_single
        → panic("Waybill line is too tall for the single-page layout.")
5.  Многостраничная упаковка:
    a. Резерв последней страницы = МАКСИМАЛЬНЫЙ суффикс: с конца
       списка берутся строки, пока их суммарная высота ≤ A_last
       (жёсткий предел).
       Ограничения резерва:
       - суффикс содержит ≥ 1 строку (иначе на последней странице
         не было бы таблицы) — если ни одна концевая строка не
         помещается в A_last → panic("Waybill line is too tall for
         the last-page layout.");
       - суффикс забирает не более n−1 строк: префикс всегда
         содержит ≥ 1 строку, т.к. первая страница (полный
         заголовок и реквизиты) обязана существовать; при
         необходимости последняя строка суффикса возвращается
         в префикс.
       Балансировка суффикс НЕ трогает: последняя страница с
       подписями не может «дополучить» строки сверху — только
       отдать, что и сделано резервом.
    b. Префикс (строки до суффикса, ≥ 1 строка) размещается на
       первой + средних страницах с балансировкой:
       - P_min = наименьшее P ≥ 0 средних страниц, при котором
         Σprefix ≤ A_first + P·A_middle (допустим P = 0: документ
         из двух страниц «первая + последняя»).
       - Перебор P = P_min, P_min+1, …, P_min+4:
           F = Σprefix / (A_first + P·A_middle) — уровень заполнения;
           мягкие бюджеты: T_first = F·A_first, T_mid = F·A_middle;
            жадная упаковка по порядку: строки кладутся на текущую
            страницу, пока used + h_next ≤ мягкого бюджета; иначе
            страница закрывается и начинается следующая средняя
            (закрытие только при used > 0; на пустую страницу строка
            кладётся безусловно — она влезает в жёсткую площадь роли
            по проверке шага 2; это исключает зацикливание на строке,
            превышающей мягкий бюджет целиком).
           Успех = все строки префикса размещены.
           Первый успешный P → результат.
       - Если ни одно P диапазона не дало успеха (неразделимость
         строк): повторить тот же диапазон жадной упаковкой по
         жёстким пределам (страница закрывается только когда
         следующая строка превышает площадь роли). Первый успех
         → результат (балансировка для этого входа отключена).
       - Если и это не удалось (невозможно на реальных данных):
         panic("Waybill pagination failed.") — новый код-путь,
         тот же класс ошибки (exit 5).
6.  К каждой странице применяется растяжение (§4.5).
```

Свойства: минимальное число страниц; первая+средние страницы
заполнены до общего уровня F — огрызков вроде «6 строк из 143»
не возникает; высокая концевая строка корректно остаётся на
средней странице (суффикс её не берёт); все ранее известные
классы ошибок (сообщения `too tall …`) сохранены. Детерминизм
полный: нет случайности, перебор P ограничен 5 итерациями ×
2 прохода.

Проверено на бумаге для проблемных входов: 6eab (143 строки) —
суффикс ~19 строк на последней, 124 строки префикса делятся
первая+средние поровну по уровню F (вместо 16/21/23/24/17/17/6);
последняя строка выше A_last — суффикс меньше, строка остаётся
на средней, паники нет.

### 4.5. Растяжение строк (только вверх, до +15%)

Конфигурация:

```typst
row-stretch: (
  max: 1.15,               // не более +15% от естественной высоты
  safety-gap: 0.5mm,       // зазор до рамки, вычитается из цели заполнения
),
```

Для каждой страницы с суммой естественных высот строк `H_p` и
доступной площадью строк данных `A_роли`:

```
s_p = min( (A_роли − safety-gap) / H_p , 1.15 )
s_p ≤ 1  → строки рендерятся с естественными высотами (без сжатия)
s_p > 1  → целевая высота строки i: t_i = h[i] · s_p
```

- Страницы, не заполненные доверху (уровень F < 1), растягиваются
  не более чем до +15%: таблица визуально полнее, но 10 строк
  никогда не растягиваются на всю страницу (ограничение заказчика)
  — свободное место снизу остаётся.
- **Сжатие строк (высоты меньше естественных) не реализуется
  намеренно**: упаковка §4.4 гарантирует, что страницы не
  переполнены, поэтому потребность сжимать не возникает; сжатие
  ниже естественной высоты создаёт риск обрезки текста в ячейке
  (`block(height)` фиксирует высоту жёстко). Заказчику это
  отклонение от формулировки «±15%» выделить в отчёте: требование
  выполнено по сути (заполнение страниц без «резины» на весь лист),
  механизм сжатия отклонён по безопасности.
- Реализация: каждая ячейка растягиваемой строки рендерится внутри
  `block(height: t_i − 2·inset)` (выравнивание ячеек сохранить:
  №/ед. по центру сверху, кол-во справа сверху, наименование слева
  сверху); границы таблицы и филл шапки не меняются. Точный приём
  фиксации высоты строки исполнитель подбирает экспериментально и
  закрепляет тестом рамки (§6.3, п.2) — суммарная высота таблицы на
  любой странице не должна выходить за `A_роли`.

### 4.6. Обработка ошибок и совместимость

- Сообщения `panic` сохранить дословно (используются операторами в
  логах): `"Waybill line is too tall to fit on one page."`,
  `"Waybill line is too tall for the single-page layout."` и т.п.;
  новые сообщения добавлять можно, существующие не переименовывать.
  Маппинг ошибок в Django идёт по коду `RENDER_FAILED` из
  JSON-диагностики (не по тексту), поэтому поведение
  `_qde_error_from_stderr` не изменится.
- Поведение пустого документа, футера-счётчика, подписей —
  без изменений относительно 2.1.0.

### 4.7. Производительность

Бюджет: рендер фикстуры `waybill-qde-500` (500 позиций) должен
укладываться в `QDE_SUBPROCESS_TIMEOUT_SECONDS` Django (15 c) с

## 8. Риски и меры

| Риск | Мера |
|---|---|
| `measure()` в `context` изменит взаимодействие с футером/счётчиком | Футер уже использует `context`; после реструктуризации проверить инвариант счётчика тестом (п.5 §6.3) |
| Фиксация высоты строки через `block(height)` конфликтует со штрихами таблицы/инсетами | Подбор приёма исполнителем + жёсткий тест рамки (п.2 §6.3) + `safety-gap` |
| Время рендера вырастет из-за построчных измерений (500 строк) | Бюджет ≤7 c (§4.7); при превышении — кэширование одинаковых строк/батчинг без смены контракта |

## 9. Открытые вопросы и осознанные отклонения (не блокируют старт)

1. **Отклонение от формулировки «±15%»**: реализовано только
   растяжение вверх (до +15%); сжатие строк отклонено — упаковка по
   измеренным высотам не переполняет страницы, а сжатие ниже
   естественной высоты создаёт риск обрезки текста (см. §4.5).
   Пользователю подтвердить или вернуть требование сжатия отдельным
   решением.
2. Порог равномерности `(max−min)/max ≤ 0.30` и правило «60% от
   среднего» — установлены архитектором; ужесточить/ослабить можно
   на визуальной приёмке.
3. Нужен ли отдельный фикстурный набор «реальные прод-данные»
   (анонимизированные срезы операций 6eab/a66c) в автотестах, или
   достаточно синтетических фикстур 1–500 (сейчас: достаточно).
